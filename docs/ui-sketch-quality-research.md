# UI 草图生成质量与延迟研究

日期：2026-11-15。范围：当前工作区的真实草图生成链路，兼顾音乐预制布局和绘制动画。

后续要求更新：用户明确要求真正的流式生成。完整方案见 `docs/ui-sketch-streaming-solution.md`，其中流式已提升为第一阶段必交付能力；本文原有 P2 排序仅保留为初次研究记录。

结论：优先用本地排版约束和组件库提高稳定性，同时减少模型调用轮次和重复输出。直接图片输入值得首先做 A/B。保留当前模型与非思考模式作为基线，速度能否保持必须通过端到端测量确认。

本次完成代码审查、官方文档核对、纯本地构造输入验证，以及 12 项已有测试。未进行真实模型 A/B，也未修改运行时代码。以下收益是待验证的工程判断，不是实测提升比例。

## 1. 当前实际链路

普通草图：

```text
选区 → PNG 导出（最长边 768）→ 上传 /files 并解析
→ 准备已启用的 MCP 工具
→ 模型调用素材查询 → 本地返回候选素材 → 模型输出元素 JSON
→ 清洗 → 等待字体 → 并行加载选中的素材
→ 转换 Excalidraw 元素 → 一次性更新画布
```

- `server/visionUi.ts:97`：先上传图片，使用 `document/file` 输入；系统提示要求先查询素材，再生成元素；最多 5 轮请求，`stream: false`、`thinking: disabled`、`max_tokens: 8192`。
- `server/deepseekFiles.ts:7`：上传采用 `rich_layout_recognition`，已有相同图片的 10 分钟缓存，最多 8 条。首次生成与重复生成应分开测。
- `server/mcpManager.ts:742`：准备工具时可能等待连接所有已启用的 MCP 服务；是否构成瓶颈取决于用户配置和连接状态。
- `src/services/aiVision.ts:119`：字体加载在素材加载之前串行等待；素材内部已有并行加载，不能把“改为并行下载素材”当作新优化。
- `src/services/aiVision.ts:167`：普通生成一次性更新画布，不是逐元素网络流式生成。

音乐分支在 `src/services/aiVision.ts:61` 命中关键词即调用本地 `buildMusicDemoScene`，随后播放动画并返回，没有调用真实模型。此处分支没有演示模式条件。`sceneMath.ts` 的动画时长限定为 1.5–5.8 秒。这一分支适合展示预制组件质量，但不能代表普通 AI 生成质量或时延。

## 2. 已确认的质量缺口

| 问题 | 代码证据 | 影响与建议 |
| --- | --- | --- |
| 文字布局信息丢失 | `visionSanitize.ts:97` 只保留文字位置、字号、字体、颜色等，未保留宽度、对齐等约束 | 保留受支持的文字盒信息，并在字体就绪后测量、换行和排版，避免长中文溢出 |
| 安全区只写在提示词 | `visionSanitize.ts:165` 按文字左上角查找图片并调整颜色，未执行 `overlayRecommended` 或 `safeArea` | 按整个文字包围盒与所属组件校验；不允许叠字时使用组件外部的标题槽位，不要盲目移动文字覆盖邻居 |
| 图片比例无约束 | `visionSanitize.ts:85` 独立接受宽高 | 固定组件槽位，按原始比例 contain 或受控 cover；裁切时同步转换安全区 |
| 层级被重新排序 | `aiVision.ts:152` 将所有容器放在所有图片下方、所有独立文字上方 | 改为组件内局部层级，避免按钮底色、遮罩等被图片盖住；绑定文字也要纳入顺序 |
| 网格与目标边界未落实 | 清洗函数无 targetSize 输入；最后只对整体偏移吸附 | 由布局器确定列宽、间距与边界；不能简单逐项取整，否则可能破坏比例与整体宽度 |
| 规范存在矛盾 | `visionUi.ts:44–53` 同时要求 390×844 和所有尺寸为 8 的倍数，示例还有 44、342 等尺寸 | 以目标尺寸为准，间距采用 8px 节奏，细部可用 4px；外框与剩余列宽允许例外 |
| 字体与风格固定 | `aiVision.ts:119,156` 强制 Excalifont；提示固定蓝色 | 提供少量完整主题，统一字号层级和语义颜色；手绘/规整字体选择需同时验证中文覆盖和文字测量 |
| 素材候选有顺序偏差 | `visionUi.ts:60` 查询后取前 12 条 | 无关键词时返回 5 hero、5 metric、2 media，profile/list 完全缺席；按类别覆盖和草图语义排序 |

本地构造验证：输入一张 `overlayRecommended: false` 的 16:9 图片并指定 120×120，叠加带 `width:80`、`textAlign:right` 的长中文标题。清洗后只修正了文字颜色，保留了叠字位置和正方形图片尺寸，并丢弃文字宽度/对齐。输入的非网格坐标和 `roughness:2` 也原样保留。这证明校正缺口存在，但不代表这些错误在真实生成中的发生率。

## 3. 推荐实施顺序

### P0：直接图片输入对照实验

当前是 PNG → 文件解析 → document。DeepSeek 官方明确指出，文件上传会等待解析完成；rich layout 会抽取文字并自动裁出图像，且不保证每张图都被检测出来。[文件解析文档](https://api-docs.deepseek.com/guides/document_parsing/)

官方同时确认 `deepseek-flash` 在 Messages API 中支持 image 输入，包括 base64。因此可对比“原始图片直接输入”与现有 document 路径：有望省掉单独的上传解析环节，并直接保留整幅草图供模型观察。需要核对用户实际配置的模型和服务商支持情况，不能只依赖默认模型名；现有已解析文件 ID 也不能直接当图片 ID 使用。[兼容性文档](https://api-docs.deepseek.com/guides/anthropic_api/)

先保持 768 输入尺寸一致，隔离变量。若小字识别仍是瓶颈，再单独比较更高分辨率和传入原始文本摘要，避免同时改变多个条件。

### P0：本地布局校正与组件层级

保留单次生成结果格式作为兼容路径，在清洗与元素转换之间增加质量检查：文字尺寸、图片比例、安全区、所属容器边界、组件层级。先修复可确定的错误；无法确定归属时保守处理，避免全局自动移动造成二次错位。

目标是在不增加模型调用的前提下提高成图合格率。新增本地处理耗时需要在 acdert 实测；建议以 p95 不超过 30ms 作为初始预算，而非声称当前已达到。acdert 暂无 Web Worker/OffscreenCanvas，不应依赖这些 API 做首版实现。

### P1：素材预选，省掉必经工具往返

把已有的草图文字摘要、用户描述和目标比例用于本地选择少量候选；文本不足时使用跨类别均衡候选。将精简目录直接附在请求里，让同一次模型调用完成识别、选材和布局，不再强制先调用 `get_ui_assets`。

不能把全部素材长描述、全部模板和所有外部 MCP 工具一股脑塞进提示词。默认候选可从 6–8 个起测；复杂需求保留按需扩展。MCP 能力按任务需求注入，显式依赖外部资源的任务仍保留工具流程。

字体准备和素材加载可并发；选中素材可缓存已完成的数据转换/解码结果。当前已有上传缓存和字体 Promise 缓存，应测冷启动与热缓存两种状态，避免重复实现。

### P1：模型输出组件意图，本地生成细节

项目已有 20 个 UI 模板（`uiTemplates.ts:329`）和 25 张素材。建议拆出 Header、Navigation、MetricCard、MediaCard、ListRow、FormField 等可复用组件；先用少量高质量版式覆盖常见需求。

示意协议（设计提案，非现有接口）：

```json
{
  "theme": "clean-blue",
  "layout": "mobile-dashboard",
  "sections": [
    { "kind": "header", "title": "今日概览" },
    { "kind": "metricRow", "items": [
      { "label": "待处理", "value": "12" },
      { "label": "已完成", "value": "28" }
    ] },
    { "kind": "list", "title": "最近任务", "items": ["整理需求", "确认排期"] }
  ]
}
```

模型负责信息结构、内容和组件选择；本地布局器负责坐标、间距、配色、字号、图层和素材槽位。减少重复颜色与尺寸字段，有望减少输出 token，同时稳定设计。仍输出可编辑 Excalidraw 元素；独特布局保留受约束的原始元素兜底，避免所有页面长得一样。

Google A2UI 官方也采用声明式数据、组件目录和增量消息。这为架构方向提供参考，不意味着需要引入整个 A2UI/CopilotKit 框架。[官方说明](https://developers.googleblog.com/build-generative-ui-apps-with-a2ui-copilotkit-agents/)

### P2：真正的渐进式渲染

DeepSeek Messages 端点支持 SSE。需完整处理 `message_start`、content block 事件、`message_delta`、`message_stop`；不能使用 Chat Completions 的 `[DONE]` 终止假设。[流式协议](https://api-docs.deepseek.com/guides/anthropic_api/#streaming)

推荐先固定页面骨架和槽位，再按完整组件渐进显示；缓存不完整 JSON，组件通过校验后才能提交。首版可尝试 50–100ms 的合并提交窗口，并通过 acdert 的绘制耗时调整。避免每个 token 触发全画布重绘；已呈现组件不要持续重排。失败/取消需恢复原草图，最终保留一次撤销语义。

流式处理主要缩短首个有意义组件出现的时间，并不自动改善最终设计，也不保证减少模型总生成时长，因此排在布局和调用轮次优化之后。绘制动画应与接收数据重叠，避免模型结束后再串行播放完整动画。

## 4. 提示词与缓存的适当角色

### 用户补充：思考模式是否值得开启

已核对用户提供的[中文思考模式文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode)。它提供 `low/high/max` 三档实际思考强度，默认开启且默认 high；当前项目显式设置 disabled，因此不受默认值影响。medium 会映射 high，不是独立的中间档。

对于当前 Anthropic Messages 请求，候选实验配置是 `thinking: { type: 'enabled' }` 配合 `output_config: { effort: 'low' }`，不是 Chat Completions 的 `reasoning_effort`。兼容性文档指出 `budget_tokens` 被忽略，因此不能用它承诺固定的思考 token 或毫秒预算。

low 值得作为受控实验，特别是复杂布局和内容层级任务；官方没有提供本项目的质量增益或速度不变保证。应先通过直接图片输入、省掉必经素材工具回合和压缩输出节省时间，再评估把部分时间用于 low 思考。与当前流程直接启用 high 相比，这更符合延迟约束。

建议分四组逐步对照：A 当前流程；B 直接图片输入；C 在 B 上预注入素材并单轮生成；D 在 C 上开启 low。对 B/C 的文本长度与素材数量设上限。每一步单独判断收益，D 仅在视觉质量提高且 p50/p95 均满足预算时采用。

开启思考后 temperature 不生效，不能通过调低 temperature 控制思考结果或时间；deepseek-flash 非思考模式下 top_p 固定为 1。若保留工具循环，Messages 协议必须保留完整 assistant content，包括 thinking/tool_use 块；本项目现有逻辑整体回传 blocks，但类型定义和流式实现仍需补全并测试。Chat Completions 文档中的 reasoning_content 字段不能直接照搬进 Messages 协议。

### 提示词与缓存

提示词保留短而可执行的设计约束和一个小型优质示例；固定主题默认值由本地展开。稳定的公共前缀有利于缓存，但缓存依赖已持久化前缀单元的完整匹配，且只提供 best-effort 命中。不能承诺加长提示词没有延迟代价。[DeepSeek 缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)

不要把 Chat Completions 的 `response_format: json_object` 直接移植到当前 Messages 请求。JSON 合法性与视觉布局质量是不同问题；是否采用工具 schema 输出应单独核对接口并测试。

第一阶段不默认增加多轮视觉评审、多个模型串行规划、实时联网找设计参考或图像生成。这些会引入额外关键路径，适合作为用户主动选择的深度精修功能。

## 5. 评估方法与验收建议

建议固定 20 份草图：手机首页、表单、列表、桌面看板、局部卡片，包含长中文、暗色背景、无文字手绘和不规则目标尺寸。每份各跑 5 次；分阶段仅改变一个变量，统一模型、采样配置、输入尺寸和运行环境。真实模型测试与本地预制音乐路径分别报告。

记录：截图导出、上传/解析、工具准备、每轮模型调用、首个完整组件、最后组件、本地排版、字体/素材准备、画布提交、绘制动画；有并行阶段时报告关键路径，不简单相加。保存模型输出 token、输入 token、缓存命中、工具轮数、失败/重试率。

质量指标：文字溢出、错误遮挡、素材拉伸、安全区违规、对齐偏差、内容完整性、草图结构保真，以及隐藏方案标签后的人工偏好。组件多或图片多不等同于设计更好。

建议把“速度尽量不变”暂定为：端到端可编辑完成时间 p50/p95 相比基线回退不超过 5%；首个有意义组件时间不变或更短；失败率不升。5% 是建议的产品验收容差，不是现有性能数据；样本不足时 p95 只能作为初筛。

首批落地组合：直接图片输入 A/B + 文字/安全区/层级校正 + 素材候选均衡；随后做素材单轮生成和组件化。最后再接真正的增量展示。
