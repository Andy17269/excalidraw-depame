# acde

> Build, run, debug, and test apps and desktops for Dopame OS with the acde CLI and its runtime, acdert. Use when a project has an acde.config.jsonc, imports an acde: module (acde:fs, acde:window, ...) or depends on @dopame/acde-api, and when the user mentions acde, acdert, or Dopame OS, or asks to create, run, inspect, screenshot, drive, or end-to-end test a Dopame app or desktop.

This is the entry file of the acde skill, as shipped with acde 0.0.9; every page linked here is plain Markdown. All of it in one file: https://docs.dopame.ai/llms-full.txt. With acde installed, `acde skills install` puts the same skill where your agent loads skills from.

A Dopame OS app is a web project: HTML, CSS, and JS in any framework, optionally with a Bun or Node.js backend. `acde` is the developer CLI (create, check, build, run, inspect, test). `acdert` is the runtime that draws the desktop and the apps; `acde dev` starts it. The relation is wrangler to workerd.

This skill ships inside acde and describes the version it came with. When it and the CLI disagree, the CLI is right: `acde` with no arguments prints the usage of every command.

## Check the environment first

Run `acde doctor`, in the project directory when there is one. It checks what follows and more (the runtime draws a test frame on the GPU), prints one line per check (`ok`, `warn`, `error` or `skip`) with a `fix:` line under each problem, and exits with code 1 on an error. Run it again whenever `acde dev`, `acde test` or the MCP `start` does not come up, before guessing. `acde doctor --fix` then fixes what acde may (the skill, `.acde/` in `.gitignore`) and asks before what downloads, installs or stops something; without a terminal it skips those unless given `--yes`, which you pass only when the user agreed. Approvals, GPU drivers and the project's code it leaves to you and the user. See [Check the setup](https://docs.dopame.ai/guide/doctor.md).

1. `acde` must be on PATH. If it is not, follow [Install](https://docs.dopame.ai/start/install.md).
2. `acde dev` and `acde test` need the runtime, acdert. The acde installer sets up the acdert release that acde pairs with next to it; acde finds `ACDERT` (a path to the binary) first, then that one, then `acdert` on PATH (in the Dopame virtual machine it is already there). If `acde doctor` finds none, or one that does not run, run the acde installer again (`acde doctor --fix --yes` does that for an installed acde); only if it cannot run on this machine, offer the steps in [Install the runtime by hand](https://docs.dopame.ai/start/install.md#install-the-runtime-by-hand), and use them only if the user agrees. Get it from nowhere else. Without it, `acde new`, `acde check`, and `acde build` still work, and `acde dev` says what is missing.
3. A project runs on Bun when its package manager is bun, and on Node.js with npm, pnpm, or yarn. `acde test` needs Bun.

## What is not like a browser

acdert has its own renderer and is not Chromium. Standard APIs follow the spec, and what the runtime lacks is absent rather than faked. Before relying on anything beyond the DOM, `fetch`, and storage, read [Web compatibility](https://docs.dopame.ai/reference/web.md). The mistakes to avoid:

- **No modules from a CDN.** ES modules load only from the app's own files (`import('https://…')` fails): bundle every code dependency. Images, stylesheets and fonts can come from other hosts, as in a browser.
- **Missing APIs**: Web Workers, Service Workers, `crypto.subtle`, WebGL, OffscreenCanvas, fullscreen, pointer lock. `confirm()` returns `false` and `prompt()` returns `null`; build dialogs in the page.
- **System access goes through `acde:` modules only** (`import { fs } from 'acde:fs'`), and only for capabilities the config requests. There is no global object. Importing a module that was not requested fails. See [Capabilities](https://docs.dopame.ai/guide/capabilities.md).
- **The backend has no TCP port.** A backend's `listen(port)` becomes a unix socket, and the page reaches it with a same-origin `fetch('/api/…')`. Do not `curl localhost`. See [Backend](https://docs.dopame.ai/guide/backend.md).
- **No developer tools.** Use the commands below to look at pages.
- **Platforms differ.** An app that requires a capability the platform lacks does not start there; one that lists it as optional gets `null` from `load()`. See [Platform support](https://docs.dopame.ai/reference/platforms.md).

## The working loop

Create a project without prompts (`--yes` asks nothing; without it `acde new` waits for answers in a terminal):

```sh
acde new my-app --template html --label "My App" --install --yes
```

Run it. `acde dev` builds, starts acdert, and rebuilds and reloads on every change. It does not exit: start it in the background and keep it running while you work; `acde stop` ends it. Add `--headless` when no window is needed; pages still render and screenshots still work. It is ready when `acde webs`, run from the project directory, lists the app's page.

```sh
acde dev --headless
```

Look at what the app does, from another shell in the project directory:

```sh
acde inspect                      # the screen as text, every visible element with a ref
acde query 'form button'          # elements by CSS selector, hidden ones too, each with a ref
acde act w1.15 click              # act on a ref: click, type, key, drag, ...
acde shot my-app -o shot.png      # a PNG of the app's window; read it to see the page
acde console --level errors       # console.error and uncaught errors
acde network --failed             # requests that failed
acde eval my-app 'document.title' # run code in the page, print JSON
```

After a change, wait for the rebuild line in the `acde dev` output, then check `acde console --level errors` and look at the page (`acde inspect` or `acde shot`) before saying it works. A failed build prints one error line and the window keeps the last good build, so a page that did not change may mean the build failed.

Write end-to-end tests in `*.e2e.ts` with the Playwright-like API from `acde/test`, and run them with `acde test`: each test gets its own isolated headless session. See [Testing](https://docs.dopame.ai/guide/testing.md).

Before handing over: `acde check` (config and entry), `acde build` (the package in `.acde/`), and `acde test` if the project has tests.

## Rules

- Edit `acde.config.jsonc`, never the generated `.acde/package.json`.
- Request a capability in the config before importing its module.
- Some capabilities need the user's approval (`terminal`, `network`, `camera`, `microphone`, `launch`, `slots`, and each shared folder named in `fs.roots`). An app that requires one opens no window until the prompt is answered: when `acde webs` lists no page, run `acde permissions`, then `acde allow`. Approving is the user's decision, and it is kept for the app: allow only what the user asked for or agreed to, and say what you allowed. See [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval).
- In `acde:fs` a root is an id, not a path. `"fs": true` gives the app its own folder, the root `private`: keep the app's working files there. See [Files and folders](https://docs.dopame.ai/guide/files.md).
- An app that lists `services` only runs in the desktop that provides them: `acde dev` in the app project alone does not start it, `acde dev --desktop <dir>` does. See [Services](https://docs.dopame.ai/guide/services.md).
- Keep `.acde/` out of git.
- In scripts and tests, select elements by role and name (the semantic tree), not by coordinates.
- An MCP server with the same tools is available as `acde mcp`; the CLI commands above need no setup, so prefer them unless the user has set MCP up. See [MCP](https://docs.dopame.ai/guide/mcp.md).

# Install

The installer sets up acde (the CLI, the project templates, and the SDK) together with the runtime it pairs with, acdert, which runs your apps. No npm, no root. See [The runtime](#the-runtime).

## With a coding agent

Give your agent this prompt:

```text
Read https://pkgs.dopame.ai/acde/install.md and follow it to set up acde on this machine.
```

The page it reads tells it to check for Bun or Node.js, run the installer below, install the acde skill for itself, and report what is ready. See [Coding agents](https://docs.dopame.ai/guide/agents.md).

## Requirements

acde runs on a JavaScript runtime you already have. Either one works:

- [Bun](https://bun.sh) 1.4 or later
- [Node.js](https://nodejs.org) 22.3 or later

If you have both, acde uses Bun. The install script doesn't install either of them for you.

`acde test` (end-to-end tests) runs on Bun only. With only Node.js, every other command works.

## Supported platforms

| System | CPU |
| --- | --- |
| macOS | Apple silicon (arm64), Intel (x86_64) |
| Linux | x86_64 |
| Windows | x64 |

acde itself is JavaScript; these are the platforms the runtime is built for (`aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`), and the installer stops with this list on any other. The Windows installer is x64 only. What the runtime can do differs somewhat between them; see [Platform support](https://docs.dopame.ai/reference/platforms.md).

## macOS / Linux

```sh
curl -fsSL https://pkgs.dopame.ai/acde/install.sh | sh
```

This installs into `~/.acde` (change it with `ACDE_INSTALL`) and adds `~/.acde/bin` to your shell's startup file (zsh, bash, fish, or `.profile`). In a terminal it shows a progress bar for each download; after each one, and also when its output is captured (a coding agent, CI), it prints the file's size and that its SHA-256 matches. A download that stalls (under 1 KB/s for 30 seconds) is retried twice, then the installer stops and installs nothing.

To leave your startup files alone:

```sh
curl -fsSL https://pkgs.dopame.ai/acde/install.sh | sh -s -- --no-modify-path
```

To install a specific version: `sh -s -- --version 0.1.0`.

## Windows

In PowerShell:

```powershell
irm https://pkgs.dopame.ai/acde/install.ps1 | iex
```

This installs into `%USERPROFILE%\.acde` and adds it to your user `Path`. Like the macOS / Linux installer, it shows each download's progress (size, speed, time left) in a terminal, prints the size and SHA-256 check of each file, and gives up on a download that receives nothing for 30 seconds after three tries. If you turned progress off (`$ProgressPreference = 'SilentlyContinue'`), it stays off.

`irm | iex` cannot pass parameters. Set environment variables before it, or run the script as a script block to pass its parameters `-Version` and `-NoModifyPath`:

```powershell
$env:ACDE_VERSION = '0.1.0'; $env:ACDE_NO_MODIFY_PATH = '1'
irm https://pkgs.dopame.ai/acde/install.ps1 | iex

& ([scriptblock]::Create((irm https://pkgs.dopame.ai/acde/install.ps1))) -Version 0.1.0 -NoModifyPath
```

## Installer options

Both installers take the same options, each in its own form:

| Option | `install.sh` | `install.ps1` |
| --- | --- | --- |
| Install a specific version (and its runtime) | `--version X.Y.Z` | `-Version X.Y.Z` or `ACDE_VERSION` |
| Leave startup files / the user `Path` alone | `--no-modify-path` | `-NoModifyPath` or `ACDE_NO_MODIFY_PATH` set to any value |
| Install somewhere else than `~/.acde` | `ACDE_INSTALL` | `ACDE_INSTALL` |

In PowerShell, environment variables set this way stay set in that terminal; remove them afterwards (`Remove-Item Env:ACDE_VERSION`) if a later install should take the defaults.

## Verify

> **Open a new terminal first.** The installer changes `PATH` only for terminals opened after it, so in the terminal you installed from, `acde` is `command not found`. To use that terminal anyway, run the last line the installer printed (`export PATH=…`, or `$env:Path = …` in PowerShell).

In the new terminal, run:

```sh
acde doctor
```

It checks what `acde dev` and `acde test` need: acde on PATH, Bun and Node.js, the runtime (found, runs, pairs with this acde, and its own check of its files and the GPU, on which it draws a test frame), and more. Each line begins `ok`, `warn`, `error` or `skip`, a line beginning `fix:` follows each problem, and the last line says whether everything is there. See [Check the setup](https://docs.dopame.ai/guide/doctor.md).

`acde --version` prints just the versions: acde, the SDK and contract level it was built with, and the runtime it found with its version and contract level.

## The runtime

`acde dev` and `acde test` run your app in the runtime, acdert. The installer puts the acdert release that this acde pairs with next to it: the binary as `bin/acdert` (`acdert.exe` on Windows) and its host files as `bin/app/`, both checked against the release's `SHA256SUMS`. The pairing is recorded with each acde release, so installing a specific version of acde (the installer's `--version X.Y.Z`, or `-Version X.Y.Z` on Windows) installs the runtime that version pairs with. If the runtime cannot be installed (no build for your platform, a failed download or checksum), the installer installs nothing and keeps what you had. Inside the Dopame virtual machine, `acdert` is already on PATH.

acde looks for the runtime in this order:

1. `ACDERT`: the path of an acdert binary, or the name of one on PATH;
2. the acdert the installer put next to acde;
3. `acdert` on PATH.

When none is there, `acde dev` stops and says so, and `acde doctor` says where it looked and what to do.

The runtime renders pages only on the GPU, so it needs a working GPU (Metal on macOS, DirectX 12 on Windows, Vulkan on Linux). On Linux that means the hardware Vulkan driver of the machine's GPU (Mesa: `vulkan-intel` or `vulkan-radeon` on Arch, `mesa-vulkan-drivers` on Debian, Ubuntu and Fedora; NVIDIA: the vendor's driver); a software renderer is not accepted. Without it `acde dev` fails at startup with a log line that begins `web layer unavailable:` and says `no usable Vulkan driver was found: install the GPU's Vulkan driver …`: install the driver and check that `vulkaninfo --summary` lists the GPU. `acde doctor` shows the same line as an error of its `gpu` check before you start anything.

### Install the runtime by hand

Use this only when the installer cannot set up the runtime, for example without access to `https://pkgs.dopame.ai/` from the machine. The result is an `acdert` binary with its `app/` directory next to it; set `ACDERT` to the path of that binary (`~/.acdert/acdert` in the commands below). Each runtime release is in `https://pkgs.dopame.ai/acdert/<version>/`, and `https://pkgs.dopame.ai/acdert/latest.json` names the latest version. A release has:

| File | What it is |
| --- | --- |
| `acdert-aarch64-apple-darwin.tar.xz` | The runtime for macOS on Apple silicon |
| `acdert-x86_64-apple-darwin.tar.xz` | The runtime for macOS on Intel |
| `acdert-x86_64-unknown-linux-gnu.tar.xz` | The runtime for Linux x86_64 |
| `acdert-x86_64-pc-windows-msvc.tar.gz` | The runtime for Windows x64 |
| `acdert-host-<version>.tar.gz` | The runtime's own scripts (an `app/` directory), the same on every platform |
| `SHA256SUMS` | Checksums of the files above |

Each runtime archive holds only the binary, `acdert` (`acdert.exe` on Windows). Releases up to 0.0.8 have the bare binary instead, under the same name without `.tar.xz` (`.exe` instead of `.tar.gz` on Windows).

Download the archive for your platform, the host archive, and `SHA256SUMS`, and check them. Extract both into the same directory: acdert looks for `app/` next to itself and does not start without it. On Linux, extracting a `.tar.xz` needs `xz` (the `xz` or `xz-utils` package).

On macOS or Linux, paste the lines below, with `target` set for your platform (the parentheses keep your terminal in its current directory): `aarch64-apple-darwin` on Apple silicon, `x86_64-apple-darwin` on an Intel Mac, `x86_64-unknown-linux-gnu` on Linux.

```sh
(
target=aarch64-apple-darwin
base=https://pkgs.dopame.ai/acdert
version=$(curl -fsSL "$base/latest.json" | sed -n 's/.*"version": *"\([^"]*\)".*/\1/p')
mkdir -p ~/.acdert && cd ~/.acdert
curl -fsSLO "$base/$version/acdert-$target.tar.xz" -O "$base/$version/acdert-host-$version.tar.gz" -O "$base/$version/SHA256SUMS"
grep -E " (acdert-$target\.tar\.xz|acdert-host-$version\.tar\.gz)\$" SHA256SUMS | sha256sum -c - &&
  rm -rf app && tar -xzf "acdert-host-$version.tar.gz" && tar -xJf "acdert-$target.tar.xz"
)
```

`sha256sum` prints `OK` for both files; if it doesn't, nothing is extracted. Then point acde at it: add this line to your shell's startup file, and run it in the current terminal too:

```sh
export ACDERT="$HOME/.acdert/acdert"
```

Adding `~/.acdert` to `PATH` works as well.

On Windows, in PowerShell:

```powershell
& {
  $ProgressPreference = 'SilentlyContinue'
  $base = 'https://pkgs.dopame.ai/acdert'
  $version = (Invoke-RestMethod "$base/latest.json").version
  $dir = "$env:USERPROFILE\.acdert"
  New-Item -ItemType Directory -Force $dir | Out-Null
  $files = 'acdert-x86_64-pc-windows-msvc.tar.gz', "acdert-host-$version.tar.gz"
  foreach ($f in $files + 'SHA256SUMS') { Invoke-WebRequest "$base/$version/$f" -OutFile "$dir\$f" }
  $sums = Get-Content "$dir\SHA256SUMS"
  foreach ($f in $files) {
    $want = (($sums | Where-Object { $_ -like "* $f" }) -split ' ')[0]
    if ((Get-FileHash "$dir\$f").Hash -ne $want) { throw "checksum mismatch: $f" }
  }
  Remove-Item -Recurse -Force "$dir\app" -ErrorAction SilentlyContinue
  tar -xzf "$dir\acdert-host-$version.tar.gz" -C $dir
  tar -xzf "$dir\acdert-x86_64-pc-windows-msvc.tar.gz" -C $dir
  [Environment]::SetEnvironmentVariable('ACDERT', "$dir\acdert.exe", 'User')
  $env:ACDERT = "$dir\acdert.exe"
}
```

This sets `ACDERT` for your user and for the current terminal.

To upgrade the runtime, run the same commands again. Check that it works with a new project:

```sh
acde new hello --template html --install --yes
cd hello
acde dev
```

### Install the Dopame desktop

On its own, `acde dev` runs only your app. To run it inside Dopame's desktop (`acde dev --desktop dopame`, `acde test --desktop dopame`), install the `dopame` desktop package too. `https://pkgs.dopame.ai/acde-dopame/latest.json` gives the latest build: its `base` is the directory with `dopame.tar.gz` and `SHA256SUMS`. The archive holds one package directory, `dopame/`; extract it into the package directory `$XDG_DATA_HOME/acde/packages` (by default `~/.local/share/acde/packages`):

```sh
(
base=$(curl -fsSL https://pkgs.dopame.ai/acde-dopame/latest.json | sed -n 's/.*"base": *"\([^"]*\)".*/\1/p')
packages="${XDG_DATA_HOME:-$HOME/.local/share}/acde/packages"
mkdir -p "$packages" && cd "$(mktemp -d)"
curl -fsSLO "${base}dopame.tar.gz" -O "${base}SHA256SUMS"
sha256sum -c SHA256SUMS &&
  rm -rf "$packages/dopame" && tar -xzf dopame.tar.gz -C "$packages"
)
```

On Windows the package directory is `%USERPROFILE%\.local\share\acde\packages`; extract the same archive there with `tar -xzf dopame.tar.gz -C <that directory>`.

Then, in your project:

```sh
acde dev --desktop dopame
```

Your app is in the desktop's app list; open it from there. The desktop's assistant needs a program that is not part of this download, so the output has a warning about it (`no assistant`); everything else works. For where the runtime looks for packages, see [Local install](https://docs.dopame.ai/guide/install.md#package-lookup).

## Upgrade and uninstall

To upgrade, run the install command again; it upgrades the runtime too. Each version is installed in `~/.acde/versions/<version>`, with its runtime in its `bin`, and `~/.acde/current` points to the one in use.

To uninstall, run `acde skills remove` if you installed the skill, delete `~/.acde`, and remove the line that was added to your shell's startup file. If you installed the runtime by hand or the desktop as above, also delete `~/.acdert` and `~/.local/share/acde/packages/dopame`, and remove the `ACDERT` line.

# First app

## Create

```sh
acde new my-app
```

In a terminal, `acde new` asks for whatever is missing: app or desktop, template, display name, whether to add a backend, whether to install dependencies, and whether to run `git init`. Press Enter at each prompt to accept the defaults.

To skip the prompts, pass everything as options and add `--yes`:

```sh
acde new my-app --template html --label "My App" --install --yes
```

Available templates:

| Template | What it is |
| --- | --- |
| `html` | A plain web page (default); add `--backend` to include a backend |
| `desktop` | A desktop (see [Desktops](https://docs.dopame.ai/guide/desktop.md)) |
| `react` `vue` `svelte` `solid` `preact` `vanilla` | create-vite templates |
| `next` `nuxt` `sveltekit` `astro` | Each framework's official scaffolding tool |

Framework templates run the latest version of the framework's scaffolding tool through your package manager, then add `acde.config.jsonc`.

## Run

`acde dev` runs your app in the runtime, acdert, which the installer set up next to acde (inside the Dopame virtual machine it is already on PATH). `acde doctor` checks that it is there and works on this machine; see [The runtime](https://docs.dopame.ai/start/install.md#the-runtime).

```sh
cd my-app
acde dev
```

`acde dev` builds the project, starts acdert, and opens a window on your computer with your app inside. Leave it running, then edit and save `index.html` or `src/main.js`; the window reloads automatically.

Press Ctrl+C or close the window to stop, or run `acde stop` from another terminal in the project directory.

> In the built-in templates, `package.json` has three scripts, `dev`, `build`, and `check`, which run `acde dev` / `acde build` / `acde check`. Framework templates leave the framework's own scripts alone and add `acde:dev`, `acde:build`, and `acde:check` instead.

## Add a capability

Let's have the app keep a file of its own. This example uses the `html` template; in a framework template, add only the `capabilities` line to its `acde.config.jsonc` (it has no `entry`, and should not get one) and put the code in one of the framework's source files.

First, request the `fs` capability in `acde.config.jsonc`:

```jsonc
{
  "type": "app",
  "id": "my-app",
  "label": "My App",
  "icon": "files",
  "entry": "index.html",
  "capabilities": { "fs": true }
}
```

Then in `src/main.js`:

```js
import { fs } from 'acde:fs'

const status = document.querySelector('#status')
await fs.writeFile('private', 'hello.txt', 'Hello from my app')
const { text } = await fs.readText('private', 'hello.txt')
const roots = await fs.roots()
status.textContent = `${text} (roots: ${roots.map((r) => r.id).join(', ')})`
```

Save, and after the window reloads you'll see `Hello from my app (roots: private)`. With `"fs": true` an app gets a private folder of its own (the root `private`) and whatever folder the user picks for it. The user's shared folders, such as Desktop and Downloads, are named in the config and approved by the user before the app gets them; see [Files and folders](https://docs.dopame.ai/guide/files.md). Importing a capability you haven't requested fails outright.

## Build and check

```sh
acde check   # check the config and entry
acde build   # build into .acde/
```

`.acde/` is the **package** the runtime understands: a directory with a `package.json` whose `acde` field is the **manifest** (what the package contains), plus the build output for the web pages and backend. To install the app into the Dopame desktop on your machine, use `acde install`; see [Local install](https://docs.dopame.ai/guide/install.md).

# Project layout

A project created with `acde new my-app --backend`:

```text
my-app/
├── acde.config.jsonc    app config: id, name, icon, entry, capabilities
├── package.json
├── index.html           entry page
├── src/main.js
├── src/i18n.js         picks the language and fills in interface text
├── src/locales/         one message table per language: en.js, zh.js
├── server.ts            backend (optional)
├── public/              static files copied as is (optional)
└── .acde/               build output, kept out of git
```

## Interface languages

The `html` and `desktop` templates keep interface text out of the markup, in one table per language under `src/locales/` (`en.js`, `zh.js`, each `export default { key: 'text' }`). `src/i18n.js` uses only the platform, no library:

- `locale` is chosen from `navigator.language`: the exact tag if there is a table for it (`zh-TW.js`), else its base language (`zh`, via `Intl.Locale`), else `en`. A key a table lacks falls back to its English text.
- `t(key, values)` returns the text with `{name}` placeholders filled in.
- `translate()` sets `<html lang>` to `locale` and fills every element with a `data-i18n="key"` attribute; `index.html` ships with `lang="en"` until then.

To add a language, add `src/locales/<tag>.js` with the same keys as `en.js` and import it in `i18n.js`. Format dates and numbers with `Intl` and `locale` (`new Intl.DateTimeFormat(locale)`). Framework templates keep the UI their own scaffolder writes.

## Config and manifest

- **`acde.config.jsonc`** is the config you write. It's only read at build time. `"type"` is `"app"` (a windowed app) or `"desktop"` (a desktop).
- The **manifest** is the `acde` field of `package.json` in the build output, `.acde/`. That directory is a **package**: what the runtime runs. The manifest is the only thing the runtime reads.

`acde build` turns the former into the latter. Most of the time you only need to care about the config; for the manifest format, see [Manifest](https://docs.dopame.ai/reference/manifest.md).

A directory without `acde.config.jsonc` can still be built:

- If the `acde` field in `package.json` has `apps`, it's treated as a **handwritten package** and used as is (only checked).
- Otherwise it's treated as a default app: the entry is `index.html`, the id is derived from `name` in `package.json`, and the display name comes from `displayName` or `productName`.

## Build output

After building the app `my-app`:

```text
.acde/
├── package.json         manifest
├── web/                 web pages, served at /app/my-app/ in the runtime
└── backend/
    ├── server.js        bundled backend
    ├── package.json     {"type": "module"}
    └── acde-listen.js   preload that turns the backend's listen into a unix socket
```

A desktop project produces `desktop/` (served at `/desktop/<id>/`), `services/<name>.js`, and `apps/<id>/{web,backend}` for the apps it bundles.

## JavaScript runtime and package manager

Whether a project runs on Bun or Node.js is decided by its package manager: `bun` → Bun; `npm` / `pnpm` / `yarn` → Node.js. For an existing project, acde looks at the lockfile, then at the `packageManager` field in `package.json`. `acde new` writes `packageManager` for you.

On Node.js, acde bundles with the project's own Vite (which is why the built-in templates add `vite` as a dev dependency under npm / pnpm / yarn); on Bun it uses `Bun.build`. The bundling rules are the same on both.

## SDK

The project's dev dependencies include `@dopame/acde-api`, the SDK version this acde was built with, as a tarball from `https://pkgs.dopame.ai/acdert/<version>/` (so the project installs on any machine and in CI). It provides:

- The JSON Schema for `acde.config.jsonc` (editor completion)
- TypeScript types for all `acde:` modules and the manifest
- `load()`: load an `acde:` module optionally
- The Vite plugin `@dopame/acde-api/vite`

To reference the types in a JS file:

```js
/// <reference types="@dopame/acde-api/app" />
```

In a TypeScript project, add `"@dopame/acde-api/app"` to `compilerOptions.types` in `tsconfig.json`. A desktop's pages use `@dopame/acde-api/shell` instead, which adds the modules only a desktop gets; `@dopame/acde-api` declares all of them.

# Configuration

A project's config lives in `acde.config.jsonc` at its root (`acde.config.json` also works). JSONC allows comments and trailing commas. A `$schema` at the top gives your editor completion and validation:

```jsonc
{
  "$schema": "./node_modules/@dopame/acde-api/config.schema.json",
  "type": "app",
  "id": "notes",
  "label": "Notes",
  "icon": "editor",
  "entry": "index.html",
  "size": [960, 640],
  "capabilities": { "fs": true }
}
```

## Apps (`"type": "app"`)

| Field | Description |
| --- | --- |
| `id` | App id: lowercase letters, digits, and `-`. Defaults to one derived from `name` in `package.json` |
| `label` | Display name, shown in the title bar and on the desktop |
| `icon` | An icon name, or a `.svg` / `.png` in the project; see [Assets and icons](https://docs.dopame.ai/guide/assets.md) |
| `entry` | Entry point: an HTML page (default `index.html`), or a module whose default export is a `WindowApp`. Omit it when building with a framework |
| `framework` | How to build; defaults to `auto`. See [Frameworks](https://docs.dopame.ai/guide/frameworks.md) |
| `capabilities` | System capabilities the app requests, such as `{ "fs": true }`; see [Capabilities](https://docs.dopame.ai/guide/capabilities.md). Some need the user's approval before the app starts |
| `optional` | Names from `capabilities` that the app can run without; they are not asked for at launch and are reached with `load()`. See [Optional capabilities](https://docs.dopame.ai/guide/capabilities.md#optional-capabilities) |
| `services` | Names of the [desktop services](https://docs.dopame.ai/guide/services.md) the app uses, e.g. `["clock"]`. The app starts only where they run |
| `size` | Default size of the window's content area, `[width, height]` in logical pixels; defaults to `[800, 600]`. The title bar is not included. A desktop opens the window at this size; a single app run by `acde dev` fills the host window, which opens at this size (see [Windows](https://docs.dopame.ai/guide/window.md#size-and-title-bar)) |
| `frame` | Whether the window has a system title bar; defaults to `true` |
| `multiple` | Whether multiple windows can be open at once |
| `mimeTypes` | File types the app can open, e.g. `["text/markdown", "image/*"]`; see [Opening apps](https://docs.dopame.ai/guide/open.md#files-and-links) |
| `schemes` | URL schemes of the links the app can open, lowercase and without the colon, e.g. `["mailto"]` |
| `requests` | Kinds of request the app accepts from other apps' `open()`, e.g. `["show-image"]`; see [Opening apps](https://docs.dopame.ai/guide/open.md#apps) |
| `heapMb` | JS heap limit per window, in MB; defaults to 256, minimum 32 |
| `backend` | The backend: `false` for none, or `{ "entry": "server.ts", "port": 3000 }`. Detected automatically by default; see [Backend](https://docs.dopame.ai/guide/backend.md) |
| `public` | Directory of static files copied as is; defaults to `public` |
| `name` / `version` | Package name and version; taken from `package.json` by default |
| `apiLevel` | The contract level the package is built for. Leave it out: `acde build` writes the level of the installed SDK |

## Desktops (`"type": "desktop"`)

| Field | Description |
| --- | --- |
| `id` / `label` / `description` | The desktop's id, name, and description |
| `entry` | The desktop page; defaults to `index.html` |
| `heapMb` | JS heap limit for the desktop page; defaults to 1024 |
| `services` | Desktop services: name → module path, or name → `{ "module": path, "modules": [shell modules] }` for a service that uses shell modules; see [Services](https://docs.dopame.ai/guide/services.md) |
| `apps` | Apps bundled with this desktop (system apps). Each entry has the same fields as an app, but `id` and `entry` are required; its `capabilities` may also name shell modules, such as `"windows": true` |

See [Desktops](https://docs.dopame.ai/guide/desktop.md).

## Check

```sh
acde check
```

This checks that the id is valid, the entry file exists, the icon is a known name or an existing image, service modules exist, and the framework is recognized. It also checks the declarations against the rules of the runtime: capability names, the shared places in `fs.roots`, `optional`, `services`, and every `acde:` import in the source against what the app declares. Errors make the command exit with 1; warnings and notes are only printed.

```text
error: app "notes": fs.roots "work" is not a shared place (desktop, documents, downloads, music, pictures, videos); any other folder is one the user picks (showDirectoryPicker() with "fs": true)
error: app "notes": capability "clock" is not a system capability; list desktop services under services
error: src/main.js:1: app "notes": acde:terminal needs "terminal" in the capabilities of Notes
error: src/main.js:2: app "notes": acde:windows is a shell module: only the desktop, its services and system apps may import it, and Notes is not a system app
```

A path in `fs.roots` is answered with the name to write instead: `fs.roots "~/Documents" is not a shared place: write "documents", the runtime finds that folder through the system (also when it was moved)`. An `optional` name that is not in `capabilities` is reported first, on its own: `error: app notes: optional "launch" is not in capabilities (optional lists declared capabilities that the app can run without)`. That line really names the app without quotes, unlike the ones above; match either form when you read these lines by program.

`acde check --platform windows` (or `macos`, `linux`) adds what that platform lacks: a required capability it does not have is an error, an optional one a note.

For the full field definitions, see [Reference: acde.config.jsonc](https://docs.dopame.ai/reference/config.md).

# Frameworks

acde doesn't ask you to change your framework's config. At build time it recognizes the framework from your dependencies, runs **the framework's own build**, and puts the output into the package. The first match wins:

| Dependency | Build command | Output |
| --- | --- | --- |
| `next` | `next build` (standalone) | `.next/standalone` as the backend; static `out/` with `output: 'export'` |
| `nuxt` | `nuxt build` (`node-server` preset) | `.output/server/index.mjs` as the backend, `.output/public` |
| `@sveltejs/kit` | `vite build` | The server is wrapped as the backend; `client` is the static assets |
| `astro` | `astro build` | `dist/`; a backend if `dist/server/entry.mjs` exists |
| `@react-router/dev` / `@remix-run/dev` | `react-router build` / `remix vite:build` | A backend if `build/server/index.js` exists |
| `@angular/core` + `@angular/cli` | `ng build --base-href /` | `dist/**/browser`; a backend if `server/server.mjs` exists |
| `vite` | Calls the project's Vite `build()` in process, reading its `vite.config` | Static pages |
| `react-scripts` | `react-scripts build` | `build/` |
| A `build` script in `package.json` | `bun run build` / `<pm> run build` | The first of `dist` / `build` / `out` / `www` / `.output/public` that contains HTML |

For server-rendered frameworks, pages are generated by the backend, and the manifest's `entry` is `/app/<id>/` (ending in `/`).

If there's no `node_modules`, acde runs `<pm> install` first.

## Detection

Use `framework` in `acde.config.jsonc`:

- `auto` (default): detect using the table above.
- `next`, `nuxt`, `sveltekit`, `astro`, `react-router`, `remix`, `angular`, `vite`, `cra`, `script`: use this one.
- `none`: no framework; acde bundles `entry` itself.

When `entry` is set, acde doesn't pick up Vite (the built-in templates depend on Vite only so acde can bundle with it). To build with Vite, remove `entry` or set `"framework": "vite"`.

## Without a framework

When no framework is recognized (or with `"framework": "none"`), acde bundles from `entry`:

- HTML entry: `base` is `/app/<id>/`, `acde:*` imports stay external, `NODE_ENV` is `"production"`, and `import.meta.env` works as in Vite (including `VITE_*` variables).
- Module entry: bundled into `<name>.js` with its exports kept; the default export is a `WindowApp`.

On Bun it uses `Bun.build`; on Node.js it uses the project's Vite (if it's missing, you're told to `add it with <pm> add -D vite`). The rules are the same on both.

## Vite plugin

If you `import { fs } from 'acde:fs'` in a Vite project, the dev server (`vite dev`, in a regular browser) doesn't know about `acde:` modules. Add the SDK's plugin:

```js
// vite.config.js
import acde from '@dopame/acde-api/vite'

export default {
  plugins: [acde()],
}
```

At build time, `acde:*` imports stay external. In the dev server they're replaced with a stub: calls reject with `only there when the app runs in acde`, and `on()` returns a no-op unsubscribe function. That way the same code still opens in a browser.

acde adds this plugin automatically when it builds a project with Vite.

## acde: modules

If the same code needs to run both in a browser and in acde, use `load()`. It returns `null` when the module isn't available:

```js
import { load } from '@dopame/acde-api'

const fs = await load('fs')
if (fs) console.log(await fs.roots())
```

# Assets and icons

## public/

The project's `public/` directory (rename it with the `public` config field) is copied as is into the app's `web/`.

References in your pages that start with `/` and point to a file in public:

- In HTML: bundled as usual.
- `url(/x)` in CSS: kept as is when the project is an app whose entry is HTML, because the runtime also serves the app's directory at `/`. Elsewhere (a desktop, or the apps it bundles) it is bundled as usual.
- If the file can't be found anywhere, the build fails and tells you which URL in which file, and what's missing from public.

## URLs

App pages have the origin `http://acde.local`. An app's files are served both under `/app/<id>/` and at `/`, so `/logo.png` and relative paths both work.

## Icons

Set `icon` to an icon name or to an image in the project:

```jsonc
{ "icon": "chart" }        // icon name
{ "icon": "assets/logo.svg" } // image in the project
```

**Icon names** refer to Dopame's built-in icon set, which matches the desktop's visual style:

`files` `browser` `editor` `office` `term` `projects` `dash` `team` `dopa` `settings` `store` `app` `timer` `cards` `list` `chart` `calc` `music` `video` `photo` `paint` `game` `chat` `mail` `calendar` `code` `book` `map` `weather`

If omitted, it's `app`.

**Images**: a value that contains `/` or `\`, or has an extension, is treated as a path relative to the project directory, and must be a `.svg` or `.png`. At build time it's copied to the app's `web/icon.<ext>`, and the manifest gets `/app/<id>/icon.<ext>`. `acde check` warns about any other value.

# Backend

An app can have a backend: a module that exports `fetch`, or any Node.js / Bun server that calls `listen()` (Express, Hono, Fastify, ...). Pages reach it with a plain `fetch('/api/…')`.

App backends run on macOS, Linux and Windows. On Windows the runtime reaches the backend in another way; see [On Windows](#on-windows).

## Write a backend

The `server.ts` generated by `acde new my-app --backend`:

```ts
export default {
  fetch(request: Request): Response {
    const url = new URL(request.url)
    if (url.pathname === '/api/hello') return Response.json({ hello: 'world', at: new Date().toISOString() })
    return new Response('not found', { status: 404 })
  },
}
```

In the page:

```js
const answer = await (await fetch('/api/hello')).json()
```

`export default { fetch }` works on both Bun and Node.js. On Node.js, acde's preload runs it with `node:http`; requests and responses are WHATWG `Request` / `Response` objects with streaming bodies. (There's no WebSocket upgrade on Node.js.)

You can also listen yourself:

```ts
import { createServer } from 'node:http'

createServer((req, res) => res.end('hi')).listen(3000)
```

## Discovery

Without a `backend` field, acde uses the first of these that exists:

`server.ts` `server.js` `src/server.ts` `src/server.js` `server/index.ts` `server/index.js` `backend/index.ts` `backend/index.js`

To set it explicitly, or turn it off:

```jsonc
{ "backend": { "entry": "api/main.ts", "port": 8080 } }
{ "backend": false }
```

`port` defaults to 3000; it's the port the backend thinks it's listening on.

## No TCP ports

An app's backend doesn't open TCP ports on the host. At build time, acde puts a preload (`acde-listen.js`) next to the backend that replaces `listen(P)` in `Bun.serve`, `Bun.listen`, and `net` / `http` / `https` / `tls` / `http2` with a unix socket at `<app's socket directory>/P.sock`. If no port is given, it uses `PORT` / `BUN_PORT` / `NODE_PORT`, and otherwise 3000.

As a result:

- Two apps can both `listen(3000)` without conflict.
- Requests from the page to same-origin paths (`/api/x`) or to `http://localhost:<port>/…` (and `127.0.0.1`, `[::1]`, `0.0.0.0`) all go to the app's own backend.
- UDP `bind` to a specific port is rejected (`EACCES`); ports opened by native extensions on their own aren't covered.

## On Windows

The same build runs on Windows, and there too the backend opens no TCP port and no named pipe. How the runtime reaches it depends on what runs it:

- **Bun**: as on macOS and Linux, `listen(P)` becomes a socket file `P.sock`. Its directory (`ACDE_APP_SOCKETS`) is made anew each time the backend starts, and only the current user and the system can open it.
- **Node.js**: Node.js cannot listen on a socket file on Windows, so nothing listens at all. The preload keeps the server that called `listen(P)`, and the runtime hands it every connection (HTTP requests and WebSocket upgrades) through a private pipe to the backend process. The backend gets `ACDE_APP_CHANNEL=fd` and no `ACDE_APP_SOCKETS`. A backend built by an acde from before this is not started on Windows; the log says `not started: acde-listen.js does not support the Windows channel (built by an older acde: acde build it again)`.

To stop a backend on Windows the runtime asks it to shut down: it takes no new connections, finishes the requests in progress and exits; after 3 seconds the runtime ends it together with the processes it started.

## Bundling

`acde build` bundles the backend into a single ES module, `backend/server.js` (target node): npm packages are bundled in, while Node built-in modules and `bun` / `bun:*` stay as imports. The same output runs on both Bun and Node.js.

## Running

- The backend starts **when the app's first window opens** and stops **when its last window closes** (on macOS and Linux with SIGTERM, then SIGKILL after 3 seconds; for Windows see [above](#on-windows)). After the 4th crash within a minute, it's no longer restarted automatically.
- It runs on Bun if `bun` is on PATH, otherwise on Node.js (≥ 22.3). `acde dev` picks based on the project's JavaScript runtime.
- The environment is built from scratch: `ACDE_APP_ID`, `ACDE_APP_DATA`, `ACDE_APP_SOCKETS`, `PORT`, `NODE_ENV=production`, plus the session's `HOME`, `PATH`, `LANG`, and so on, and the proxy variables below. Nothing else is inherited from your terminal.
- Proxy settings are passed on. If the session sets any of `http_proxy`, `https_proxy` or `all_proxy`, the backend gets `http_proxy`, `https_proxy`, `all_proxy` and `no_proxy` as the session has them (on macOS and Linux under both the lower-case and the upper-case names, as set; on Windows, where variable names ignore case, under the upper-case names). If none is set, the backend gets the system's manual proxy, the same settings pages use. Only Windows and macOS have one: on Windows the HTTP proxy from the user's Internet settings (a `socks=` entry becomes `all_proxy=socks4a://host:port`), set under the upper-case names; on macOS the HTTP, HTTPS and SOCKS proxies from the network settings (SOCKS becomes `socks5h://host:port`), set under both the lower-case and the upper-case names. `no_proxy` then holds the session's `no_proxy`, the system's exceptions in `no_proxy` form (`*.example.com` becomes `.example.com`, `192.168.*` becomes `192.168.0.0/16`; other wildcards, Windows' `<local>` and macOS's "exclude simple hostnames" have no `no_proxy` form and are left out), and `localhost,127.0.0.1,::1`. A proxy auto-config script or automatic proxy discovery answers per URL and can't be expressed as variables, so with those the backend gets no system proxy (on Windows, "Automatically detect settings" alone still passes the manual proxy). The settings are read each time a backend starts. Linux has no system proxy setting to read: only the session's variables count there. Your HTTP client still has to honour these variables (Bun's `fetch` and many npm clients do; Node.js's built-in `fetch` does not by default).
- The working directory is `$XDG_DATA_HOME/acde/apps/<id>/`; the app can keep its own data here.
- Backend output goes to the runtime's log, prefixed with `[<id>#backend]`. `acde dev` prints it in your terminal.

## Running it directly

To debug the built backend on its own, without the runtime, give it a socket directory and load the preload that `acde build` put next to it (the commands are for macOS and Linux):

```sh
acde build
cd .acde/backend
ACDE_APP_SOCKETS=/tmp/my-app-sockets bun --preload ./acde-listen.js server.js
curl --unix-socket /tmp/my-app-sockets/3000.sock http://localhost/api/hello
```

# Capabilities

Pages only get the standard Web APIs. There is exactly one way into system capabilities: the built-in `acde:` modules, imported the same way as `node:fs`:

```js
import { fs } from 'acde:fs'
import { window } from 'acde:window'
import fs2 from 'acde:fs' // the default export is the same object
```

There is no `acde` global, and the runtime never attaches anything non-standard to `window`.

Talking to other hosts needs no capability: `fetch`, `WebSocket`, and the other standard APIs work as usual, through the system's proxy when one is set. See [Web compatibility](https://docs.dopame.ai/reference/web.md#network).

## Requesting capabilities

The `capabilities` in your config decide which modules an app can import:

```jsonc
{
  "capabilities": {
    "fs": true,
    "openFiles": true,
    "open": ["notes", "viewer"]
  }
}
```

| Capability | Grants | The user approves it |
| --- | --- | --- |
| `fs` | `acde:fs`. `true`: the app's private folder and the folders the user picks for it. `{ "roots": ["downloads", … ] }` adds shared places; see [Files and folders](https://docs.dopame.ai/guide/files.md) | Each shared place, as `fs.<place>` |
| `terminal` | `acde:terminal`: pseudo-terminals | Yes |
| `network` | `acde:network`: network settings, Wi-Fi (Linux only, including Dopame OS) | Yes |
| `office` | `acde:office`: office document service (Linux only) | |
| `open` | Opening other apps with `acde:open`. `true` for any app, or a list of app ids | |
| `openFiles` | `acde:openPath` / `acde:handlers`, and `open(request)` without a target app: a file or a link goes to its default app | |
| `launch` | `start` in `acde:launch`: start native programs | Yes |
| `slots` | `embed` in `acde:launch`: native programs embedded in your own window (Dopame OS only) | Yes |
| `camera` / `microphone` | `navigator.mediaDevices.getUserMedia()` video / audio (not on Windows) | Yes |

Every app can import these without requesting anything: `acde:window` (its own window), `acde:capabilities` (what it has, see [below](#acdecapabilities)), `acde:apps` (`list()` and `open()`), and `acde:open` (opening another app still needs `open`).

A name that is not in the table is an error in `acde check`:

- **Desktop services** are listed under `services`, not under `capabilities`: `"services": ["clock"]`, then `import { clock } from 'acde:clock'`. The app then starts only in a desktop that runs the service. See [Services](https://docs.dopame.ai/guide/services.md).
- **Shell modules** (`acde:windows`, `acde:packages`, `acde:session`, `acde:desktops`, `acde:inspect`, `acde:desktop`, `acde:setDefault`, `acde:permissions`) belong to the desktop. Only the desktop page, its services, and the apps bundled with a desktop (system apps) get them; see [Desktops](https://docs.dopame.ai/guide/desktop.md#system-apps).

Importing a module the app has no right to fails with a `TypeError` that names the missing declaration, and `acde check` and `acde build` report the same thing for every `import` in your source before anything runs:

```text
error: app "notes": capability "clock" is not a system capability; list desktop services under services
error: src/main.js:1: app "notes": acde:terminal needs "terminal" in the capabilities of Notes
error: src/main.js:2: app "notes": acde:windows is a shell module: only the desktop, its services and system apps may import it, and Notes is not a system app
```

Calling a method the app has no right to is rejected with `status: 403` (`code: 'forbidden'`), for example `open('mail')` when `open` lists only other apps.

## Approval

Some capabilities need the user's consent as well as the declaration: `terminal`, `network`, `launch`, `slots`, `camera`, `microphone`, and each shared place named in `fs.roots` (`fs.downloads`, `fs.documents`, ...). The apps bundled with a desktop (system apps) are not asked.

- **When**: a required capability is asked for before the app's first launch, one prompt per capability, one at a time. Until every prompt is answered the app opens **no window**. Nothing answers a prompt automatically. (An [optional](#optional-capabilities) one is asked for when the page requests it.)
- **In a dev session**: `acde dev` prints a line like `Notes (notes) waits for the user to allow "terminal" (prompt 1; answer it with acde allow or acde deny, …)`, and `acde webs` lists no page for the app. Answer with `acde allow` or `acde deny`; see [Debugging](https://docs.dopame.ai/guide/tools.md#approvals). In a desktop, the desktop shows the prompt (see [Desktops](https://docs.dopame.ai/guide/desktop.md#approval-prompts)); tests answer with `acde.allow()` (see [Testing](https://docs.dopame.ai/guide/testing.md#approvals)).
- **Allowed**: the decision is stored per app (`$XDG_CONFIG_HOME/acde/permissions.json`) and the user is not asked again.
- **Denied**: the app does not start. `acde dev` of a single app logs `acdert app notes: Notes: "terminal" is denied by the user; acdert app asks for it again the next time it runs` and exits with code 1; the next `acde dev` of that app asks again (`Notes (notes) was denied "terminal" in an earlier run: asking again`). In a desktop the denial is stored like an approval: the app leaves the app list (`acde:apps` fires `changed`), and `apps.open()` rejects with `status: 403`, `code: 'denied'` and the message `Notes: "terminal" is denied by the user`, the call that raised the prompt and every later one.
- **Taking a decision back**: `acde revoke <app> <capability>` (or the desktop, through `acde:permissions`) removes it, whether it was an approval or a denial. In the session that is running, the capability then counts as denied: its calls fail with `status: 403`, `code: 'denied'`, and the error's `capability` names it. An app that required it leaves the app list and cannot be opened or reloaded: in a desktop a reload closes its window, and a session that runs the app alone ends at its next reload with the line a denial logs. The user is asked again when the runtime starts the next time.

## Optional capabilities

Everything in `capabilities` is required by default: if the platform lacks one, or the user denies one, the app does not start. List the ones the app can run without in `optional`:

```jsonc
{
  "capabilities": { "terminal": true },
  "optional": ["terminal"]
}
```

- The app starts without asking the user, and it also starts on a platform that lacks the capability.
- An optional module must not be imported statically (`acde check`: `acde:terminal is optional ("terminal" is in optional): reach it with load('terminal') from @dopame/acde-api instead of importing it`). Get it with `load()`, which resolves to `null` while the module is unavailable.
- A capability that needs approval is asked for when the page calls `request(name)` from `acde:capabilities`. Its state is `not-asked` until then and `asking` while the prompt waits; `request()` resolves with the capability's status once the user has answered. Only when the user allowed it (`state: 'available'`) does `load()` return the module from then on; when the user denied it, the state is `denied` and `load()` keeps resolving to `null`.
- `load()` gives `null` without a reason. A dynamic `import('acde:terminal')` rejects with a `TypeError` that says where the approval stands: `acde:terminal: "terminal" is not asked for yet; ask for it with acde:capabilities request("terminal")`, `acde:terminal: "terminal" is waiting for the user's answer`, or `acde:terminal: "terminal" is denied by the user`.
- `camera` and `microphone` have no module to load: the page calls `navigator.mediaDevices.getUserMedia()`, which raises the prompt itself when the capability was not asked for yet. See [Web compatibility](https://docs.dopame.ai/reference/web.md#media).

```js
import { load } from '@dopame/acde-api'
import { capabilities } from 'acde:capabilities'

let terminal = await load('terminal') // null until the user has allowed it
if (!terminal) {
  const status = await capabilities.request('terminal') // asks the user
  if (status.state === 'available') terminal = await load('terminal')
}
```

Making `fs` optional makes its shared places optional too: `load('fs')` works at once with the private folder, and `request('fs.downloads')` asks for a place.

## acde:capabilities

```js
import { capabilities } from 'acde:capabilities'

capabilities.level // 1: the contract level of the runtime
capabilities.platform // 'linux' | 'darwin' | 'win32'
capabilities.mode // 'session' (Dopame OS) | 'desktop' (a desktop in the host window) | 'standalone' (a single app in the host window)
capabilities.get('terminal') // { name, kind: 'system' | 'service', state, reason, optional }
capabilities.list() // the same for every system capability and every service the app lists
await capabilities.request('terminal') // asks the user if needed; resolves with the status
```

| `state` | Meaning |
| --- | --- |
| `available` | Declared, this platform has it, and the user allowed it if it needs approval |
| `not-asked` | Needs approval, and the user was not asked yet: `request()` asks |
| `asking` | The approval prompt waits for the user's answer |
| `not-declared` | Not in the app's `capabilities` / `services` |
| `unsupported` | This platform, or this way of running, lacks it |
| `service-not-running` | The desktop service is not running |
| `shell-only` | A shell module, and the app is not a system app |
| `denied` | The user denied it or took the approval back |

`request()` of a capability that needs no approval, or that the user already answered, resolves at once with the current status.

# Windows

Each app window is a separate web page with its own DOM and JS heap; one window crashing does not affect the others. All windows of the same app share storage such as `localStorage`, IndexedDB, and cookies.

## Size and title bar

- In a desktop, a new window's content area is the configured `size` (800 × 600 by default) and opens centered; next time it opens where it was last closed.
- In an `acde dev` session that runs a single app (an app project without `--desktop`), the app **fills the host window**, and `size` sets how large that window opens: with `"size": [400, 300]` the host window's content area is 400 × 300. The title bar is drawn inside it, so the page is 400 × 268. Without `size` the host window takes most of the screen (90% of its width and 85% of its height, at most 1440 × 900).
- `acde dev --headless` has no host window, and `size` is not applied: the screen is 1440 × 900 (1280 × 800 in `acde test`) and the app fills it, so the page is 1440 × 868. To see the app in a window of its own `size`, run it in a desktop: `acde dev --desktop ./my-desktop`, or `--desktop dopame` once that desktop is installed (see [acde dev](https://docs.dopame.ai/guide/dev.md#what-runs)).
- The title bar drawn by the system is **not part of the page's document**: `innerHeight`, `100vh`, and `resize` events only cover the content area. To drop the title bar, set `"frame": false` in the config, draw your own, and use `setGrabHint` to tell the system where the window can be dragged.
- The title comes from `document.title` or `window.setTitle()`, whichever was set last (a `<title>` in the page replaces a title set before the document loaded); if neither is set, `label` is used.

## acde:window

```js
import { window as self } from 'acde:window'

self.setTitle('Untitled — Notes')

self.on('beforeclose', async () => {
  if (!dirty) return true
  return confirmDiscard() // return false to keep the window open
})
```

> The module is named `window`, the same as the global `window`, so renaming it on import keeps things clear.

| Member | Does |
| --- | --- |
| `id` | This window's id (a number) |
| `setTitle(title)` | Sets the title |
| `setMenus(menus)` | App menus (shown in the desktop's menu bar) |
| `close()` | Closes the window at once; `beforeclose` is not asked |
| `minimize()` | Minimizes the window, as `requestState('minimized')` does; the promise rejects with `status: 409`, `code: 'unavailable'` when the window cannot be minimized |
| `state` / `requestState(state)` | The window's state: `normal`, `minimized`, `filled` (fills the work area), `fullscreen`; see [Window state](#window-state) |
| `requestMode(mode)` | Whether the user can move and resize the window: `free` (both), `fixed` (move only), `pinned` (neither) |
| `output` | The screen the window is on: `{width, height, scale, workArea: {x, y, width, height}}` in logical pixels; `workArea` leaves out what the desktop's panels reserve. In a session that runs a single app the screen is the host window: with `"size": [400, 300]`, `output` and its `workArea` are both 400 × 300 |
| `requestAttention()` | Requests attention (for example a bouncing Dock icon; up to the desktop) |
| `requestActivate()` | Brings the window to the front and requests focus; the system may turn this into a request for attention |
| `setGrabHint(rect, edges?)` | Pressing in this area makes the system move the window (no `edges`) or resize it (with edges) |
| `setBackdrop(rect, effect?)` | Frosted glass over whatever is behind this area: `{radius, blur, saturate, brightness}`; `null` removes it |
| `requestGrab(kind)` / `releaseGrab(kind)` | Takes exclusive pointer or keyboard input (`'pointer'` / `'keyboard'`) |
| `shortcut(combo)` / `unshortcut(combo)` | Registers an app-level global shortcut, such as `'ctrl+shift+k'` |
| `hostControls` | `true` when the host system draws the window's minimize / maximize / close buttons, so a frameless app should hide its own |
| `minimizable` | `false` when this window cannot be minimized. In a session that runs a single app, on macOS and headless, the app's window is such a window: it fills the host window |

### Window state

Full screen is a **state** of the window, not a mode: `requestMode('fullscreen')` throws a `TypeError` (`requestMode: full screen is a window state, use requestState('fullscreen')`).

```js
self.on('state', ({ state, previous }) => {
  document.body.dataset.windowState = state
})

self.requestState('fullscreen') // 'normal' | 'minimized' | 'filled' | 'fullscreen'
```

- `requestState()` returns nothing. The system decides: when it refuses, nothing changes and no event arrives. A `fixed` window can only be minimized, and a `pinned` one cannot change state. A window whose `minimizable` is `false` cannot be minimized: `requestState('minimized')` changes nothing, and `minimize()` rejects.
- The state also changes without the page asking: the title bar's buttons, the desktop minimizing the window, the user bringing a minimized window back. Keep the UI in step with the `state` event (or `self.state`), not with what the page last requested.
- A minimized window that gets the focus again returns to the state it had before (`fullscreen`, for example).
- In a single-app `acde dev` session the app already fills the host window, and state requests may change nothing (headless on macOS, `minimized`, `filled` and `fullscreen` all leave the state `normal`, and no event arrives). Try states in a desktop session.
- The standard Fullscreen API (`element.requestFullscreen()`) is not supported; it rejects with `NotSupportedError`.

### Events

Subscribe with `on(name, handler)`, which returns an unsubscribe function. A name the module does not have throws a `TypeError` (`acde:window has no nosuch event (activate, deactivate, beforeclose, request, suspend, resume, grab, grablost, state, output, hostcontrols, minimizable, shortcut)`). Events are not dispatched on the global `window`.

| Event | When |
| --- | --- |
| `activate` / `deactivate` | The window gains / loses focus |
| `state` | The window's state changed, `{state, previous}` |
| `output` | The screen or its work area changed; the handler gets the new `output` |
| `beforeclose` | The user or the desktop wants to close the window. Return `false` (or resolve to `false`) to keep it; if there is no answer within 3 seconds, it closes |
| `request` | Another app or the system asks this window to open something (see [Opening apps](https://docs.dopame.ai/guide/open.md)) |
| `shortcut` | A registered shortcut was pressed, `{key}` |
| `grab` / `grablost` | Exclusive input was answered, `{kind, granted}` / taken back, `{kind: 'lost', reason}` |
| `hostcontrols` / `minimizable` | `hostControls` / `minimizable` changed; the handler gets the new value |

# Files and folders

There are three ways to read and write files:

1. **Standard file pickers**: `showOpenFilePicker`, `showSaveFilePicker`, `showDirectoryPicker`, `<input type="file">`. No capability needed; you get whatever the user picks.
2. **`acde:fs`**: files by "root": the app's own private folder, shared folders the user approved (Downloads, Documents, ...), and folders the user picked. Suited to apps like file managers and editors. Requires the `fs` capability.
3. **Private storage**: `navigator.storage.getDirectory()` (OPFS), IndexedDB, `localStorage`, for the app's own data.

An app works with handles and root ids, not with absolute paths; only the desktop and its bundled system apps see paths.

## File pickers

They work just like in a browser:

```js
const [handle] = await window.showOpenFilePicker({
  types: [{ description: 'Markdown', accept: { 'text/markdown': ['.md'] } }],
})
const text = await (await handle.getFile()).text()
```

- The dialog is the system's own (the open / save panel on macOS, the file dialog on Windows, the portal on Linux).
- Only this page can read and write the picked file.
- A folder picked with `showDirectoryPicker()` is also **granted to the app**: it shows up as a root in `acde:fs` (`source: 'granted'`) and is still there on the next launch. The default pick is read-only (the root has `mode: 'read_only'`); `showDirectoryPicker({ mode: 'readwrite' })` gives a writable one. Give it back with `fs.revoke(id)`.
- When the user cancels, the promise rejects with `AbortError`. A headless session has no dialog: a picker rejects with `AbortError` there too, unless a test answered it in advance (`chooseFiles`, `chooseFolder`, `chooseSaveFile`; see [Testing](https://docs.dopame.ai/guide/testing.md)).

## acde:fs

```jsonc
{ "capabilities": { "fs": true } }
```

```js
import { fs } from 'acde:fs'

const roots = await fs.roots()
// [{ id: 'private', label: '…', source: 'private', mode: 'writable', reason: null, exists: true }]

await fs.writeFile('private', 'notes/todo.md', '- buy milk\n', { mkdirs: true })

const { entries } = await fs.list('private', 'notes')
const { text, modifiedMs } = await fs.readText('private', 'notes/todo.md')
await fs.writeFile('private', 'notes/todo.md', text + '- a new item\n', { ifModifiedMs: modifiedMs })
```

### Roots

The first argument of every call is a root's **`id`**, and the second is a path under that root. A root's `id` is an opaque name, not a path: `fs.list('/home/me/Downloads')` is rejected.

There are three kinds of root:

| `source` | `id` | What it is | How the app gets it |
| --- | --- | --- | --- |
| `private` | `private` | The app's own data folder, created on first use | `"fs": true` (or any `fs` value) |
| `place` | The place's name, such as `downloads` | A shared folder of the user | Name it in `fs.roots`; the user approves each one (see [Shared places](#shared-places)) |
| `granted` | `folder-` plus 16 hex digits | A folder the user picked | `showDirectoryPicker()` |

`roots()` returns one item per root the app can use now: `{id, label, source, mode, reason, exists}`, plus `place` (the place's name) for a shared place. `label` is a name to show the user (the folder's name for a picked folder). `mode` is `writable`, `read_only` (a folder picked without `mode: 'readwrite'`), or `unavailable`; when it is `unavailable`, `reason` says why (`the folder does not exist`) and `exists` is `false`.

Find a picked folder's root by the handle's name:

```js
const handle = await window.showDirectoryPicker({ mode: 'readwrite' })
const picked = (await fs.roots()).find((root) => root.source === 'granted' && root.label === handle.name)
await fs.writeFile(picked.id, 'export.txt', 'hello')
```

**Keep working data in `private`.** It needs no approval and no picker, it is always writable, and it is not a root of any other app. Use a shared place or a picked folder only for files the user should find outside the app. On disk the private folder is `$XDG_DATA_HOME/acde/files/<app id>/`, which is handy when debugging; the app itself only knows it as `private`.

### Shared places

```jsonc
{ "capabilities": { "fs": { "roots": ["downloads", "documents"] } } }
```

`fs.roots` lists shared places by name: `desktop`, `documents`, `downloads`, `music`, `pictures`, `videos`. Anything else fails `acde check`: `fs.roots "work" is not a shared place (desktop, documents, downloads, music, pictures, videos); any other folder is one the user picks (showDirectoryPicker() with "fs": true)`, and for a path, `fs.roots "~/Documents" is not a shared place: write "documents", the runtime finds that folder through the system (also when it was moved)`. `private` and picked folders come with every `fs` value and are not listed.

Each named place is a capability of its own, `fs.<place>` (`fs.downloads`), and the user must approve it:

- The user is asked before the app's first launch, one place at a time. Until every prompt is answered, **the app opens no window**; `acde dev` prints a line like `Notes (notes) waits for the user to allow "fs.downloads" …`. In a dev session, answer with `acde allow` or `acde deny`; see [Debugging](https://docs.dopame.ai/guide/tools.md#approvals).
- If the user denies a place, the app does not start. A single-app `acde dev` then logs `acdert app notes: Notes: "fs.documents" is denied by the user; acdert app asks for it again the next time it runs`, exits with code 1, and asks again the next time it is started. In a desktop, the `apps.open()` that raised the prompt rejects with `Notes: "fs.documents" is denied by the user` (`status: 403`, `code: 'denied'`), and the denial is kept until it is taken back: the app leaves the app list, and opening it again rejects the same way. See [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval).
- Once approved, the place is in `roots()` as `{ id: 'downloads', source: 'place', place: 'downloads', … }` and its `id` works as the first argument: `fs.list('downloads')`. When the folder does not exist on this machine, the root has `mode: 'unavailable'` and calls on it reject with `ENOENT`.
- If the user takes the approval back while the app runs, the place leaves `roots()` and calls on it reject with `denied` (see [Errors](#errors)).

To start without asking and ask only when the user needs the place, make `fs` optional. The app then gets `acde:fs` through `load()`, with `private` and picked folders working at once, and asks for a place with `request()`:

```jsonc
{ "capabilities": { "fs": { "roots": ["downloads"] } }, "optional": ["fs"] }
```

```js
import { load } from '@dopame/acde-api'
import { capabilities } from 'acde:capabilities'

const fs = await load('fs')

const status = await capabilities.request('fs.downloads') // asks the user
if (status.state === 'available') {
  const { entries } = await fs.list('downloads')
}
```

See [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval) for the approval model.

### Paths

The second argument is a **relative path** under the root, separated by `/`; `''` (or leaving it out in `list`) is the root itself. Absolute paths, and escaping the root with `..` or a symbolic link, are rejected.

### Common calls

| Call | Returns |
| --- | --- |
| `roots()` | The roots the app can use now |
| `list(root, path?, hidden?)` | `{root, path, entries, truncated}`; hidden entries are included unless `hidden` is `false` |
| `stat(root, path)` | `{name, kind, size, modifiedMs, path}` (does not follow symbolic links) |
| `readText(root, path)` | `{text, modifiedMs, size}`, up to 64 MiB, `EILSEQ` if not UTF-8 |
| `readBytes(root, path)` | `{data: Uint8Array, modifiedMs, size}` |
| `writeFile(root, path, data, options?)` | Writes text or bytes; returns the entry `{name, kind, size, modifiedMs}` |
| `mkdir(root, path, {recursive?})` | Creates a folder |
| `rename(root, from, to)` | Renames / moves inside one root |
| `delete(root, path)` | Deletes a file or an empty folder: `{status: 'deleted', path}` |
| `copy(fromRoot, fromPath, toRoot, toDir)` | Copies a file or a folder into the folder `toDir` of another root (or the same one); returns the new entry and its `path`. A taken name gets a number (`todo 2.md`) |
| `revoke(id)` | Gives back a folder the user picked |

To bring a file from a shared place or a picked folder into the app's own data, copy it: `await fs.copy('downloads', 'report.txt', 'private', '')`.

### Safe writes

Options for `writeFile`:

- `create`: `'always'` (default, creates the file if missing), `'new'` (`EEXIST` if it already exists), `'never'` (`ENOENT` if it does not exist).
- `ifModifiedMs`: skips the write and fails with `ECONFLICT` if the file's modification time differs from this value. Remember `modifiedMs` when you read and pass it when you write, and you will never overwrite someone else's changes.
- `mkdirs`: creates the parent folders first. Without it, writing into a folder that does not exist fails with `EINVAL`.

Writes go to the original file in place (keeping its inode and permissions) and are fsynced afterwards.

### Errors

On failure the promise rejects with an `Error` that has a `code` and a `status`:

| `code` | `status` | When |
| --- | --- | --- |
| `EINVAL` | 400 | Invalid arguments, an absolute path or one that escapes the root, a missing parent folder, wrong type, symbolic link |
| `EACCES` | 403 | The first argument is not one of the app's roots, the root is read-only, or the system does not allow it |
| `not_asked` | 403 | The root is a shared place of an optional `fs` that the user was not asked about yet: `request('fs.<place>')` asks. The error also has `capability` (`fs.downloads`) |
| `asking` | 403 | The prompt for that place waits for the user's answer; the error has `capability` |
| `denied` | 403 | The user denied that place or took the approval back; the error has `capability` |
| `ENOENT` | 404 | Does not exist |
| `EEXIST` | 409 | Already exists |
| `ECONFLICT` | 409 | Changed or deleted by someone else after it was opened |
| `ENOTEMPTY` | 409 | Deleting a non-empty folder |
| `EFBIG` | 413 | Exceeds the size limit |
| `EILSEQ` | 400 | `readText` read something that is not UTF-8 |
| `ENOSPC` | 507 | Disk full |
| `EIO` | 500 | Anything else |

```js
try {
  await fs.writeFile(root, path, text, { ifModifiedMs })
} catch (e) {
  if (e.code === 'ECONFLICT') askToReload()
  else throw e
}
```

What the common mistakes look like:

| Mistake | Rejection |
| --- | --- |
| A path as the root: `fs.list('/tmp')` | `EACCES`: `this app may not use the files of /tmp (not one of its roots)` |
| A place that is not in `fs.roots`: `fs.list('downloads')` with `"fs": true` | `EACCES`: `this app may not use the files of downloads (not one of its roots)` |
| A place of an optional `fs` before `request('fs.downloads')`: `fs.list('downloads')` | `not_asked`: `Notes: "fs.downloads" is not asked for yet; ask for it with acde:capabilities request("fs.downloads")` |
| The same call while the prompt waits | `asking`: `Notes: "fs.downloads" is waiting for the user's answer` |
| A place the user denied or took back: `fs.list('downloads')` | `denied`: `Notes: "fs.downloads" is denied by the user` |
| An absolute path as the second argument: `fs.readText('private', '/etc/hosts')` | `EINVAL`: `path must be relative to the workspace` |
| `..` out of the root: `fs.readText('private', '../x')` | `EINVAL`: `path escapes the workspace` |
| Writing into a folder that does not exist, without `mkdirs` | `EINVAL`: `parent directory is missing or outside the workspace` |
| Writing to a folder picked without `mode: 'readwrite'` | `EACCES`: `<folder> was picked read-only` |
| `fs.locate(path)` or `fs.openPath(root, path)` (they turn paths into roots and back) | `EACCES`: `fs.locate() works only in system apps that declare shared places` |

## Dropped files

When files or folders are dragged from the host system into a window, the page receives the standard drag events, ending in `drop`, and `dataTransfer` carries the files the standard way. The page gets no path.

- Each dropped file or folder is an item of `dataTransfer.items` with `kind: 'file'`; `item.getAsFileSystemHandle()` resolves to a **read-only** `FileSystemFileHandle` or `FileSystemDirectoryHandle` (`createWritable()` rejects with `NotAllowedError`).
- Files up to 64 MiB are also in `dataTransfer.files`. Folders and larger files are not; use their handles.
- `dataTransfer.types` is `['Files']`; there is no `text/uri-list` or `text/plain` with the paths.

To keep a dropped file, copy its content into `private`:

```js
import { fs } from 'acde:fs'

addEventListener('dragover', (event) => event.preventDefault())
addEventListener('drop', async (event) => {
  event.preventDefault()
  const items = [...event.dataTransfer.items].filter((item) => item.kind === 'file')
  const handles = await Promise.all(items.map((item) => item.getAsFileSystemHandle()))
  for (const handle of handles) {
    if (handle.kind !== 'file') continue
    const file = await handle.getFile()
    await fs.writeFile('private', `inbox/${file.name}`, new Uint8Array(await file.arrayBuffer()), { mkdirs: true })
  }
})
```

A handle (from a drop, a picker, or an open request) can also be handed to another app; see [Opening apps](https://docs.dopame.ai/guide/open.md#files-and-links).

# Opening apps

## Apps

```jsonc
{ "capabilities": { "open": ["viewer"] } }
```

```js
import { open } from 'acde:open'

const { window } = await open('viewer', { kind: 'show-image', image: '/photos/cat.png' })
```

The second argument is a **request**: a structured-cloneable object with a `kind`, handed to the other app. `open('viewer')` without a request just opens the app (or brings its window to the front). Setting the `open` capability to `true` allows any app; a list allows only the apps listed.

The app being opened says which kinds of request it accepts in its config, and receives them through the `request` event:

```jsonc
{ "id": "viewer", "requests": ["show-image"] }
```

```js
import { window as self } from 'acde:window'

self.on('request', (request) => {
  if (request.kind === 'show-image') showImage(request.image)
})
```

`requests` lists the app's own request kinds (lowercase words such as `show-image`). The runtime checks only the `kind`; the receiving app checks the rest of the object. An app with no `requests` accepts none.

For a window opened for a request, the request is delivered once, to the first `request` handler only; a request that arrives before any handler is registered is held and delivered when one is. An app that is not `multiple` and already runs gets the request in its existing window.

`open(app, request, { parent, modal })` makes the new window a child of one of your own windows (`parent` is a window id, such as `self.id`), centered over it; `modal: true` keeps input away from the parent until the child closes.

What goes wrong:

| Call | Rejection (`status`, `code`) |
| --- | --- |
| `open('mail')` when `open` does not allow `mail` | 403 `forbidden`: `Notes may not use open mail (not in its manifest's capabilities)` |
| A request without `kind` | 400 `untyped_request`: `a request to viewer needs a kind` |
| A `kind` that is not in the target's `requests` | 409 `not_accepted`: `viewer does not accept other-kind requests (its manifest's requests)` |

To list the installed apps, use `acde:apps`; its `open` is the same function:

```js
import { apps } from 'acde:apps'

const installed = await apps.list() // [{ id, label, icon, script }]
```

## Files and links

An app declares the file types and the link schemes it can open in its config:

```jsonc
{
  "id": "notes",
  "mimeTypes": ["text/markdown", "text/plain"],
  "schemes": ["mailto"]
}
```

When the user double-clicks a `.md` file in the file manager, or another app asks for it to be opened, the system picks an app in this order:

1. The default app the user has set (XDG MIME Applications spec, `mimeapps.list`);
2. The first app whose `mimeTypes` lists the type (an exact type wins over `text/*`);
3. A native program (Dopame OS / Linux), or the system's default program (the host window on macOS and Windows).

The chosen app receives a **system request**. A file arrives as `{ kind: 'open-file', handle }`, where `handle` is a standard `FileSystemFileHandle` (or a directory handle); a link arrives as `{ kind: 'open-link', url }`. The app gets no path:

```js
self.on('request', async (request) => {
  if (request.kind === 'open-file') showText(await (await request.handle.getFile()).text())
  if (request.kind === 'open-link') compose(request.url)
})
```

Apps that request `openFiles` can hand a file or a link to its default app themselves. Leave out the app id and the system picks:

```js
import { open } from 'acde:open'

await open({ kind: 'open-file', handle }) // a handle from a picker, a drop, or a request
await open({ kind: 'open-link', url: 'mailto:someone@example.com' })
```

With an app id (`open('viewer', { kind: 'open-file', handle })`) the request goes to that app; this needs `open` rather than `openFiles`, and is rejected with 409 `not_accepted` when the target does not declare the file's type in `mimeTypes` or the link's scheme in `schemes`. A read-only handle (from a drop) stays read-only for the receiver.

`acde:openPath` and `acde:handlers` (also `openFiles`) work with a path or a URI instead of a handle:

```js
import { openPath } from 'acde:openPath'
import { handlers } from 'acde:handlers'

await openPath('/home/me/Notes/todo.md')
const { mime, association, handlers: list } = await handlers('/home/me/Notes/todo.md')
```

They suit the desktop and system apps, which know paths. For an ordinary app the file must be inside one of its `acde:fs` roots, or the call is rejected with 404 `outside_roots`; an app that holds handles uses `open({ kind: 'open-file', handle })`.

Changing the default app for a type is `setDefault(association, app)` from `acde:setDefault`, a shell module for the desktop and system apps (`association` is the value `handlers()` returned).

File types are detected with shared-mime-info, so a dev session on macOS gets the same results as Dopame OS (for example, `.md` is `text/markdown`). On macOS this needs `brew install shared-mime-info`; without it, a one-line warning is printed.

# Desktops

The Dopame OS desktop is itself an acde project: a web page that fills the screen behind every window. A desktop can import every `acde:` module this platform has except `acde:window` (which is for app windows), including the shell modules that apps do not get, and is responsible for the "system UI": the Dock, the menu bar, window switching, notifications, approval prompts, and so on. The desktop that ships with Dopame is called `dopame`; you can build your own.

```sh
acde new my-desktop --template desktop
cd my-desktop
acde dev
```

## Configuration

```jsonc
{
  "$schema": "./node_modules/@dopame/acde-api/config.schema.json",
  "type": "desktop",
  "id": "my-desktop",
  "label": "My Desktop",
  "entry": "index.html",
  "services": { "clock": "services/clock.ts" },
  "apps": [
    { "id": "hello", "label": "Hello", "icon": "app", "entry": "apps/hello/index.html" }
  ]
}
```

- `services`: [desktop services](https://docs.dopame.ai/guide/services.md) running in the background, name → module.
- `apps`: apps that ship with this desktop, with the same fields as an app project (`id` and `entry` are required). They are [system apps](#system-apps).

For editor types in a desktop project, reference the shell entry point of the SDK: `/// <reference types="@dopame/acde-api/shell" />`.

## Apps

```js
import { apps } from 'acde:apps'

for (const app of await apps.list()) {
  const button = document.createElement('button')
  button.textContent = app.label
  button.onclick = () => apps.open(app.id)
  dock.append(button)
}

apps.on('changed', ({ apps }) => render(apps))
```

`app.icon` is an icon name or an image URL; the desktop decides how to draw it. An app that cannot run here is not in the list: one that requires a capability this platform lacks, or one whose required capability the user denied. `changed` fires with the new list when it changes, also when the user denies a capability an app requires or takes its approval back.

`apps.open(id)` asks the user first when the app needs an approval (see [Approval prompts](#approval-prompts)), and rejects when the app cannot start: with `status: 403`, `code: 'denied'` (`Viewer: "launch" is denied by the user`) when the user denies that prompt, and every time after it while the denial stands; with `status: 404`, `code: 'unsupported_app'` (`Viewer needs "network" (unsupported on this platform)`) for an app that requires what this platform lacks. The desktop also imports `acde:openPath`, `acde:handlers`, and `acde:setDefault` (see [Opening apps](https://docs.dopame.ai/guide/open.md#files-and-links)). Installing packages and listing native programs are in `acde:packages` (`refresh`, `install`, `natives`, `runNative`).

## Windows

```js
import { windows } from 'acde:windows'

windows.on('open', (e) => addToTaskbar(e.window))
windows.on('close', (e) => removeFromTaskbar(e.window))
windows.on('state', (e) => markMinimized(e.window, e.state === 'minimized'))

await windows.focus(id)
await windows.requestState(id, 'minimized')
await windows.animate(id, { opacity: 0, scale: 0.9, duration: 180, easing: 'ease-out' })
```

Window events: `open` `close` `title` `state` `activate` `minsize` `parent` `menus` `crash` `hang` `responsive` `attention` `ready` `show` `animated`. Any other name throws a `TypeError`. Each event is `{type: 'window<name>', window, …}`.

A window's state is `normal`, `minimized`, `filled`, or `fullscreen`. The runtime carries out state changes itself, whether the app asked (`minimize()`, `requestState()`), the user pressed a title bar button, or the desktop called `windows.requestState(id, state)`; the desktop learns of every change from the `state` event (`{window, state, previous}`). `windows.list()` gives every window with its current `state`. `windows.focus(id)` or `windows.show(id)` on a minimized window brings it back in the state it had before. Hiding (`hide` / `show`) is separate from the state and only the desktop can do it. A window that hangs (`hang`) can be ended with `kill`; `close(id)` asks the app first (its `beforeclose`).

## Panels

For things that must float **above** app windows, such as the Dock, the menu bar, and popovers, use `pin` to turn an element of the desktop page into its own always-on-top window:

```js
import { desktop } from 'acde:desktop'

const panel = desktop.pin(document.querySelector('#dock'), { margin: 8, reserve: { edge: 'bottom' } })
// The system re-measures automatically when the element changes; you can also do it by hand:
panel.update()
panel.reserve({ edge: 'bottom', thickness: 64 }) // or null to reserve nothing
panel.unpin()
```

The element stays in the same document, so its state, React tree, and events work as usual. The element must be a stacking context (for example, `position` plus `z-index`, or `isolation: isolate`); its `backdrop-filter` becomes real frosted glass across windows.

`reserve` keeps a strip along one edge of the screen (`top`, `bottom`, `left`, `right`) free of filled windows: the work area shrinks by it, `filled` windows follow, and apps see the new `workArea` in `acde:window`'s `output`. Without `thickness` the strip reaches from the edge to the far side of the panel. A panel without `reserve` takes no space.

## Title bars

The runtime draws the title bar of every app window; the desktop sets how it looks and behaves:

```js
desktop.setDoubleClick('fill') // double-clicking a title bar: 'fill' | 'minimize' | 'none'
desktop.setFrameTheme({
  active: { background: '#202030', title: '#ffffff' },
  inactive: { background: '#2a2a35', title: '#a0a0b0' },
  buttonStyle: 'glyphs', // or 'dots'
  buttonSide: 'right', // or 'left'
  titleAlign: 'start', // or 'center'
})
desktop.setFrameTheme(null) // back to the default look
```

Colors are `#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`, `rgb()` or `rgba()`; each of `active` and `inactive` takes `background`, `title`, `line`, and `buttons`. Every call gives the whole theme. Unknown values throw a `TypeError`.

## Notifications, downloads, and shortcuts

```js
desktop.on('notification', (n) => toast(n.title, n.body, n.icon))
desktop.on('download', (d) => showDownload(d.name, d.path))

await windows.shortcut('ctrl+alt+t', 'desktop')
desktop.on('shortcut', ({ key }) => { if (key === 'ctrl+alt+t') apps.open('term') })
```

Shortcut scopes: `session` (highest, cannot be overridden) → app-level shortcuts of the focused window → `desktop`. On conflicts, the first registration wins.

## Approval prompts

Some capabilities need the user's approval before an app gets them (see [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval)). The desktop shows the prompts and passes the answers on with `acde:permissions`:

```js
import { permissions } from 'acde:permissions'

const ask = async (prompt) => {
  // prompt: { id, app, label, capability, reason: 'launch' | 'request' }
  const allow = await showPrompt(`Allow ${prompt.label} to use ${prompt.capability}?`)
  await permissions.answer(prompt.id, allow)
}

permissions.on('prompt', ask)
for (const prompt of await permissions.pending()) ask(prompt) // prompts raised before the page subscribed
```

`permissions.list(app?)` returns the stored decisions (`{app, label, capability, decision: 'granted' | 'denied'}`; a folder the user picked for an app is listed as `fs.folder-…` with `folder: {label, exists}`), and `permissions.revoke(app, capability)` takes one back, resolving to `false` when there was none. The `answered` event (`{id, app, capability, allowed}`) reports each answer.

## System apps

The apps in a desktop's `apps` ship in the same package as the desktop, which makes them **system apps**. They differ from other apps in three ways:

- They may declare shell modules as capabilities and import them: `"capabilities": { "windows": true, "permissions": true }`. An app outside a desktop package that declares one fails `acde check` (`acde:windows is a shell module: only apps of a desktop package (system apps) may declare it`).
- The user is not asked to approve their capabilities.
- With shared places in `fs.roots`, their `acde:fs` roots carry the folder's `path`, and `fs.locate()` / `fs.openPath()` work.

A system app imports only what it declares: `import 'acde:session'` without `"session": true` fails with `acde:session is a shell module: declare "session" in the capabilities of <label>`.

## Other modules

- `acde:session`: `logout()`, `reboot()`, `poweroff()`, `setLanguage(tag)`.
- `acde:desktops`: `list()`, `choose(id, remember?)` to switch desktops.
- `acde:launch`: `start(argv)` runs a native program, `embed(argv)` embeds one in a window (Dopame OS only).
- `acde:inspect`: turns the screen into a text semantic tree and acts on it by ref (for AI agents). See the [reference](https://docs.dopame.ai/reference/modules.md#acdeinspect).

## Developing in a desktop

While developing an app, you can also run it inside a desktop:

```sh
acde dev ./my-app --desktop ./my-desktop
acde dev ./my-app --desktop dopame
```

See [acde dev](https://docs.dopame.ai/guide/dev.md).

# Services

A desktop service is a JS module that starts and stops with the desktop and runs in the background. It exposes its methods as `acde:<namespace>` modules, one for each key of its `api` (usually just one, named after the service), callable by the desktop and by apps that list the service. It is a good home for global state and for logic that talks to external processes (an AI assistant or a sync service, for example).

## Write a service

```ts
// services/clock.ts
import type { ServiceFactory } from '@dopame/acde-api'

const clock: ServiceFactory = (ctx) => {
  ctx.log('clock started')
  return {
    api: {
      clock: {
        now: () => Date.now(),
        async uptime() {
          return new Promise((resolve) => {
            ctx.spawn(['uptime'], { onLine: resolve })
          })
        },
      },
    },
    close() {
      ctx.log('clock stopped')
    },
  }
}
export default clock
```

Register it in the desktop's config, under the service's name:

```jsonc
{ "type": "desktop", "services": { "clock": "services/clock.ts" } }
```

A service that uses shell modules is written as an object that also lists them; see [Shell modules in a service](#shell-modules-in-a-service).

## Call it

The desktop imports it directly; an app must list the **service name** in its `services`:

```jsonc
{ "services": ["clock"] }
```

```js
import { clock } from 'acde:clock'

console.log(await clock.now())
```

A service an app lists is required, and cannot be made optional: where the service is not running the app does not start (`Notes needs "clock" (service not running)`). That includes `acde dev` of the app project alone, which runs no desktop; run the app in the desktop that has the service: `acde dev ./my-app --desktop ./my-desktop`. Listing a service under `capabilities` instead is an error in `acde check` (`capability "clock" is not a system capability; list desktop services under services`).

Each key of `api` is a module name (a namespace), and its value is a set of methods. All calls are asynchronous, and arguments and return values must be structured-cloneable; callback functions can be passed across.

Names:

- An app lists the **service's name**, and gets every namespace of that service: with `api: { clock: …, timer: … }` in the service `clock`, an app that lists `clock` imports both `acde:clock` and `acde:timer`. Never list a namespace: an app that lists `timer` requires a service of that name and does not start (`Notes needs "timer" (service not running)`).
- `acde check` and `acde build` cannot know a service's namespaces (they are what the factory returns at run time). An import of the service's own name passes silently. An import of any other name that is not a system module passes with a note in an app that lists a service, and the exit code stays 0:

  ```text
  note: src/main.js:1: app "notes": acde:timer resolves only if the service Notes lists ("clock") provides the "timer" namespace
  ```

  If no listed service provides it, the import throws a `TypeError` when the page loads (`'acde:timer' is not given to …`). In an app that lists no service, the same import is an error: `error: src/main.js:1: app "notes": acde:timer is not a system module; if a desktop service provides it, list that service's name in the services of Notes`. A service with one namespace, named after the service, gets no note.
- A service cannot have the name of a system module or capability (`fs`, `open`, `window`, `windows`, `apps`, `launch`, `desktop`, `session`, `capabilities`, `notifications`, ...): `acde check` says `service "fs" has the name of a system module (acde:fs); system module names are reserved`. A namespace with such a name is left out when the service starts, and the runtime logs a line that ends, word for word, `[clock] acde.fs is taken; left out` (it writes the namespace as `acde.fs`, with a dot).

## ServiceContext

The `ctx` passed to the factory function:

| Field | What it is |
| --- | --- |
| `name` | The service name |
| `package` | The desktop package's directory |
| `state` | This service's own state directory (`$XDG_STATE_HOME/acde/<package>/<service>`), already created |
| `env` | Environment variables |
| `log(line)` | Writes a log line, prefixed with `[<service name>]` |
| `spawn(argv, options?)` | Starts a child process |
| `inspect` | The `acde:inspect` interface |
| `import(specifier)` | A shell module the desktop grants this service; see below |

`spawn` takes the options `{cwd, env, onLine(line), onExit(code, signal)}` and returns `{pid, write(text), end(), kill(signal?)}`. The child process runs in its own process group and its stderr goes to the log; when the service closes, it gets SIGTERM, then SIGKILL 3 seconds later.

A service should only use `ServiceContext` and standard Web APIs. Put heavy work in a process started with `spawn`.

## Shell modules in a service

A service cannot `import` an `acde:` module; the build rejects it:

```text
acde: service clock: services/clock.ts imports acde:windows: a service gets shell modules from ctx.import('acde:<name>'), listed in its modules in acde.config.jsonc ("services": { "clock": { "module": "<file>", "modules": ["<name>"] } })
```

It asks its context for the shell modules the desktop grants it. Grant them in the desktop's config: write the service as an object with its module file and the shell modules it may use.

```jsonc
{
  "type": "desktop",
  "services": {
    "clock": { "module": "services/clock.ts", "modules": ["windows"] }
  }
}
```

```ts
// services/clock.ts
import type { ServiceFactory } from '@dopame/acde-api'

const clock: ServiceFactory = async (ctx) => {
  const { windows } = await ctx.import('acde:windows')
  windows.on('open', (event) => ctx.log(`window ${event.window} opened`))
  return {
    api: {
      clock: {
        now: () => Date.now(),
        windows: () => windows.list(),
      },
    },
  }
}
export default clock
```

With one app window open, `clock.windows()` answers `[{ "id": 1048576, "appId": "tools", "title": "Tools", "web": true, "state": "normal" }]`.

`modules` takes the names of shell modules. Anything else is an error in `acde check` and `acde build`:

```text
error: services in acde.config.jsonc: service "clock": modules lists shell modules (windows, packages, session, desktops, inspect, desktop, setDefault, permissions)
```

`acde build` writes the grant into the desktop's entry of the package manifest as `{ "name": "clock", "modules": ["windows"] }`; a handwritten package writes that entry itself (see [Manifest](https://docs.dopame.ai/reference/manifest.md#desktopmanifest)).

What `ctx.import()` gives:

| Module | In a service |
| --- | --- |
| `acde:windows` | The whole module, as the desktop page has it: `list()`, the events, `requestState()`, and the rest |
| `acde:packages` | The whole module, with its `changed` event |
| `acde:session`, `acde:desktops`, `acde:inspect`, `acde:setDefault` | The whole module |
| `acde:desktop` | `apps()` only: a service has no page to pin panels from |
| `acde:permissions` | Not given: `acde:permissions is not available to services here` |

`ctx.inspect` needs no grant. `ctx.import()` rejects with a `TypeError` for a shell module the service is not granted (`acde:session is a shell module: list it in the modules of service "clock" in the desktop manifest`) and for anything that is not a shell module (`import(acde:fs): a service imports shell modules (acde:windows, acde:packages, …)`). A factory that lets the rejection through does not start its service; the runtime logs `[clock] not started: TypeError: …`.

# acde dev

```sh
acde dev
```

This does three things:

1. Builds the project (into `.acde/`).
2. Starts acdert, which opens **one** window on your computer: the **host window**, standing in for the screen of a Dopame OS machine.
3. Watches the project's files, and on every change rebuilds and reloads the affected windows.

A running `acde dev` is a **dev session**: the [debugging commands](https://docs.dopame.ai/guide/tools.md), [MCP](https://docs.dopame.ai/guide/mcp.md), and `acde test` all work with one.

## What runs

| Command | What you get |
| --- | --- |
| `acde dev` (app project) | Just this app, filling the host window; closing the app ends the session |
| `acde dev` (desktop project) | This desktop |
| `acde dev --app ID` | Picks one app when the project has several |
| `acde dev ./a ./b` | Several projects together, in one desktop |
| `acde dev ./app --desktop ./my-desktop` | The app runs in the given desktop project |
| `acde dev ./app --desktop dopame` | The app runs in the `dopame` desktop, once it is [installed](https://docs.dopame.ai/start/install.md#install-the-dopame-desktop) |

With several projects or `--desktop`, the desktop is chosen like this: the value of `--desktop`; otherwise the only desktop project among them; otherwise `dopame`. A `--desktop` value that looks like a path (contains `/`, or is `.` / `..`), or that names a project in the current directory, is treated as one more project.

The session is ready when `acde webs`, run from the project directory, lists the app's page. An app that requires a capability the user must approve (a shared folder named in `fs.roots`, `terminal`, `network`, ...) opens no window until its prompt is answered: `acde dev` prints a line like `Notes (notes) waits for the user to allow "fs.downloads" (prompt 1; answer it with acde allow or acde deny, …)` and waits, and `acde webs` lists no page and names what waits. Answer from another terminal with `acde allow` or `acde deny`; see [Approvals](https://docs.dopame.ai/guide/tools.md#approvals).

`--headless` doesn't open a window (a **headless session**), which suits scripts and CI. Pages still render and screenshots still work. It still needs a GPU, so it doesn't run on Linux CI machines without one (macOS CI runners work); see [Platform support](https://docs.dopame.ai/reference/platforms.md).

## Reloading

- Changes within 150 ms are merged into one build, and only the project that changed is rebuilt.
- Apps: the window is closed and reopened at its previous position and size (or the new `size`, if that changed in the config). Desktops: the desktop page reloads; services are not restarted.
- State survives a reload where possible: form values, scroll position, focus, and selection are restored.
- A failed build prints a single error line, and windows keep showing the last good build.
- Changes in `node_modules`, `.acde`, `.git`, framework output directories such as `dist` / `build` / `.next`, `*.e2e.*` test files, and `__screenshots__` do not trigger a build.

## Build output

By default the build goes into the project's `.acde/`. `--out DIR` changes that: an absolute path is used as is, and a relative path is resolved against **the project being built**. Dev session builds reach acdert only through `ACDE_PATH`; they are **not** installed into the local package directory.

## Stopping

`acde dev` ends on Ctrl+C, when you close the window, or when acdert exits. Its exit code is the same as acdert's. To end one running in the background, run `acde stop` from the project directory (or `acde stop --session <pid>`): it asks acdert to quit, waits for `acde dev` to exit, and prints `acde: stopped acde dev <pid>`.

## Logs

The terminal shows builds and reloads, the pages' `console.*` output and uncaught errors (`[<app>#<window>] page error: …`), and backend output (`[<app>#backend]`).

To watch them from another terminal, or to read them from a script, use `acde console` / `acde network` from the [debugging tools](https://docs.dopame.ai/guide/tools.md).

## Runtime

`acde dev` runs the acdert named by `ACDERT` (a path, or a name on PATH), otherwise the acdert the installer put next to acde, otherwise the `acdert` on PATH. `acde --version` shows which one it finds, and `acde doctor` checks that it runs here; see [The runtime](https://docs.dopame.ai/start/install.md#the-runtime) and [Check the setup](https://docs.dopame.ai/guide/doctor.md).

When acdert exits before the session is ready (for example because it cannot use the GPU), `acde dev` prints its log line, then `acde: acdert exited (1) before it was ready; acde doctor checks the runtime, the GPU and this setup`, and exits with that code.

# Check the setup

`acde doctor` checks what `acde dev` and `acde test` need on this machine and says how to fix what is wrong; `acde doctor --fix` fixes what acde may fix itself. Run it after installing, in a project you are about to work on, and whenever `acde dev`, `acde test` or the MCP `start` does not come up.

```sh
acde doctor
```

```text
ok     acde: 0.0.9 on Bun 1.4.4 (/Users/me/.acde/versions/0.0.9)
ok     PATH: acde on PATH is this one (/Users/me/.acde/bin/acde)
ok     Bun and Node.js: Bun 1.4+ at /Users/me/.bun/bin/bun; Node.js 22.3+ at /opt/homebrew/bin/node
ok     acdert: acdert 0.0.9 (contract level 1) at /Users/me/.acde/versions/0.0.9/bin/acdert (installed next to acde)
ok     contract level: level 1 on both sides (acdert 0.0.9, SDK 0.0.9)
ok     host files: /Users/me/.acde/versions/0.0.9/bin/app/dist
ok     gpu: Apple M3 Pro (Metal, integrated GPU): drew a test frame in 38 ms
ok     acde dev sessions: none running
ok     project: notes, app (acde.config.jsonc): acde check finds nothing wrong
ok     platform: macos (desktop, standalone) has every required capability
ok     dependencies: installed with bun (runs on Bun 1.4+), @dopame/acde-api 0.0.9
ok     git: .acde/ (the build output) is ignored
ok     agent skill: current in /Users/me/.agents/skills/acde, /Users/me/.claude/skills/acde
acde doctor: everything acde needs is here
```

Each line is `<status> <check>: <what it found>`:

| Status | Meaning |
| --- | --- |
| `ok` | Fine |
| `warn` | Works, but something will get in the way; a `fix:` line follows |
| `error` | `acde dev` or `acde test` will not work; a `fix:` line follows when there is one |
| `skip` | Not checked: there is no project here, or the check needs one that failed |

The last line counts errors and warnings. The exit code is 1 when any check is an error, else 0. `acde doctor <dir>` checks the project in `<dir>` instead of the current directory (a directory with no acde project is then an error), and `--online` adds whether a newer acde is out.

## What it checks

| Check | What it looks at |
| --- | --- |
| `acde` | The version of acde and the JavaScript runtime it runs on |
| `PATH` | Whether the `acde` on PATH is this one, not another install or checkout |
| `Bun and Node.js` | Bun 1.4+ and Node.js 22.3+ on PATH; `acde test` and projects that use bun need Bun |
| `acdert` | The runtime `acde dev` would run (`ACDERT`, else the one installed next to acde, else PATH), and whether it runs |
| `contract level` | Whether the runtime runs the contract level this acde builds, and whether it is the release this acde pairs with |
| `host files`, `gpu`, `display` | The runtime's own check, `acdert doctor`: its host files, the GPU (it draws a small frame and reads it back), and on Linux whether a host window can open |
| `acde dev sessions`, `approval` | The running `acde dev` sessions, and every app that waits for an approval, which opens no window until the prompt is answered |
| `project` | `acde check` of the project |
| `platform` | Whether this platform has every capability the project's apps require |
| `dependencies` | The project's dependencies are installed (also when a workspace keeps them in a parent directory), its runtime is on PATH, and its `@dopame/acde-api` is the version this acde is built with |
| `git` | Whether git ignores `.acde/` |
| `agent skill` | Whether the acde skill is installed for coding agents and current |
| `latest release` | With `--online`: whether a newer acde is out |

## Common findings

No runtime:

```text
error  acdert: acde dev needs the Dopame runtime (acdert) and found none: no /Users/me/.acde/versions/0.0.9/bin/acdert, which the acde installer puts there: run the installer again, set ACDERT to an acdert binary, or put acdert on PATH
       fix: run the installer again: curl -fsSL https://pkgs.dopame.ai/acde/install.sh | sh (it puts the acdert that pairs with acde next to it)
```

A runtime that does not start reports why: a missing system library (`it exited with code 127: … error while loading shared libraries: …`), a file that is not executable (`EACCES`), or on macOS a binary that a download left in quarantine, with `xattr -d com.apple.quarantine <path>` as the fix.

A runtime from before `acdert doctor` cannot check its files and the GPU:

```text
warn   runtime check: acdert 0.0.8 cannot check itself (it has no acdert doctor), so its GPU and host files were not checked
```

A runtime that cannot draw is an error of the `gpu` check, with the same reason `acde dev` would log at startup after `web layer unavailable:`. On Linux without the GPU's Vulkan driver:

```text
error  gpu: the system has a GPU (card0, kernel driver xe) but no usable Vulkan driver was found: install the GPU's Vulkan driver (for example vulkan-intel, vulkan-radeon, nvidia-utils) or point VK_DRIVER_FILES at its ICD (wgpu: No suitable graphics adapter found; …)
```

Install the driver (see [The runtime](https://docs.dopame.ai/start/install.md#the-runtime)); there is no software fallback. When it works, the line names the GPU, the graphics API and the driver, such as `ok     gpu: Intel(R) Graphics (PTL) (Vulkan, integrated GPU, driver Intel open-source Mesa driver Mesa 26.2.5-arch3.1): drew a test frame in 41 ms`.

On Linux in a shell with no graphical session (over SSH, for example):

```text
warn   display: neither WAYLAND_DISPLAY nor DISPLAY is set, so acdert app and acdert desktop cannot open a host window here: they would try to start a session on the screen (DRM) instead
       fix: run acde dev --headless, or run it inside a graphical session
```

An app that waits for an approval:

```text
warn   approval: notes waits for approval of terminal in acde dev 4242, so it opens no window until the prompt is answered
       fix: acde allow (or acde deny): approving is the user's decision
```

## Fix what it can

`acde doctor --fix` runs the checks, prints them, then fixes what it can and checks again:

| Fix | When | Asks first |
| --- | --- | --- |
| `acde skills install` | The acde skill is not installed for any coding agent, or an installed one is outdated or broken | No |
| Add `.acde/` to the project's `.gitignore` | git does not ignore the build output | No |
| Remove and make again the sessions directory | It is a link or a file, not a directory | No |
| Run the installer of this acde version again (`install.sh --version <this version> --no-modify-path`, `install.ps1 -Version … -NoModifyPath` on Windows) | The runtime next to acde is missing, does not run, is of another contract level or release, or lacks its host files; only for an installed acde, and not when `ACDERT` names the runtime | Yes: it downloads the runtime and replaces the install, all or nothing, as the installer always does |
| The project's install (`bun install`, `npm install`, …) | Its dependencies are not installed | Yes: it downloads packages and runs their install scripts |
| `acde stop --session <pid>` | A running `acde dev` does not answer | Yes: it ends a process you started |

In a terminal it asks about each fix in the last column. Without a terminal (a script, a coding agent) it skips them and says so, `skipped: … (it asks first: pass --yes to allow it)`, unless it is given `--yes`. A coding agent passes `--yes` only when the user agreed.

It never touches what is the user's to decide: an app that waits for an approval, a GPU driver or a system library, a binary in macOS quarantine, another acde on PATH, the project's code and config. Those keep their `fix:` line.

```text
fixing: install the acde skill for the coding agents found here (acde skills install)
acde: skill linked to /Users/me/.agents/skills/acde (Cline, Codex, …)
fixed: install the acde skill for the coding agents found here (acde skills install)
skipped: install the project's dependencies (bun install in /Users/me/notes) (it asks first: pass --yes to allow it)
acde doctor: after fixing:
ok     acde: 0.0.9 on Bun 1.4.4 (/Users/me/.acde/versions/0.0.9)
…
```

## acde dev points here

When `acde dev` finds no runtime, its error ends with `(acde doctor checks the whole setup)`. When the runtime exits before the session is ready, `acde dev` prints the runtime's log line and then:

```text
acde: acdert exited (1) before it was ready; acde doctor checks the runtime, the GPU and this setup
```

## In scripts and agents

`acde doctor --json` prints one object:

```json
{
  "ok": false,
  "checks": [
    { "id": "acdert", "title": "acdert", "status": "error", "summary": "…", "fix": "…" }
  ]
}
```

`ok` is false when a check is an error. A check that `--fix` can repair carries `"repair": {"action", "target", "ask", "does"}` (`ask` is true for the fixes that ask first), and with `--fix` the object also has `"fixed": [{"repair", "result", "said"}]`, `result` being `fixed`, `failed` or `skipped`; the progress lines then go to stderr. The ids are `acde`, `path`, `runtimes`, `acdert`, `contract`, `runtime` (when the runtime cannot check itself), `runtime.host`, `runtime.gpu`, `runtime.display`, `sessions`, `approval`, `project`, `platform`, `dependencies`, `gitignore`, `skill` and `latest`; `fix` is left out when there is none. The MCP server has the same check as its `doctor` tool, and the fixes that do not ask as `doctor_fix` (it names the others and leaves them to the user); see [MCP](https://docs.dopame.ai/guide/mcp.md).

The runtime's part also runs on its own, `acdert doctor` (or `acdert doctor --json`), with the same exit codes.

# Debugging

acdert has no browser developer tools. Instead, a set of commands connects to a running `acde dev` session and lets you look at pages, run code, take screenshots, and click buttons. Run them in another terminal:

```sh
acde webs
```

```text
NAME           KIND     APP    WINDOW   TITLE
desktop        desktop  -      0        My Desktop
notes#1048576  app      notes  1048576  Notes
```

## Sessions

These commands find an `acde dev` session in this order: `--session <pid>`; otherwise the session whose project directory contains the current directory; otherwise the only session, if there is just one; otherwise they fail and list all sessions.

## Commands

| Command | What it does |
| --- | --- |
| `acde webs` | Lists the running pages (one per window) |
| `acde eval <web> <code>` | Runs code in a page and prints the result as JSON; Promises are awaited. With `-` as the code, reads it from stdin |
| `acde shot <web> [-o FILE]` | Screenshot of one window (PNG) |
| `acde screen [-o FILE]` | Screenshot of the whole screen, all windows together |
| `acde inspect [--window W] [--find TEXT] [--all] [--offscreen]` | Turns the screen into text: the window list and the element tree of the focused window (`--all`: every window that is not marked `[minimized]`, and elements hidden by `opacity: 0` or `visibility`) |
| `acde query <selector> [--window W] [--ref REF] [--limit N]` | Finds elements by CSS selector, including ones `inspect` leaves out, and prints a ref for each |
| `acde act <ref> <action> [arg]` | Clicks, types, presses keys, and more on a ref from `inspect` or `query` |
| `acde console [--web W] [--level L] [--since S] [--follow]` | The pages' `console.*` output and uncaught errors |
| `acde network [--web W] [--failed] [--since S] [--follow]` | The pages' fetch / XHR / WebSocket / EventSource requests and their image, stylesheet and font loads; the kind column says which |
| `acde permissions` | Lists the approval prompts that wait and the decisions made; see [Approvals](#approvals) |
| `acde allow` / `acde deny` `[<prompt id> \| <app> <capability>] [--all]` | Answers a waiting approval prompt |
| `acde revoke <app> <capability>` | Takes back a decision |
| `acde stop` | Ends the session; see [Stopping](https://docs.dopame.ai/guide/dev.md#stopping) |

A **web** is one page: the desktop page, or the page in one app window (each window has one). `<web>` is a web name from `acde webs` (`notes#1048576`), an app id (that app's first window), or `desktop`.

### eval

```sh
acde eval notes 'document.title'
acde eval notes 'import("acde:fs").then(m => m.fs.roots())'
echo 'localStorage.length' | acde eval notes -
```

On Windows, `acde` is `acde.exe`, which hands its arguments to the CLI exactly as the shell passed them. What a shell passes differs:

- PowerShell 7: double quotes inside a single-quoted argument arrive unchanged (`acde eval notes 'document.querySelector("#x").textContent'`).
- Windows PowerShell 5.1 drops double quotes inside arguments to every program; there, write them as `\"` (the first line below).
- cmd has no single-quoted strings: put the argument in double quotes and write the double quotes inside it as `\"` (the second line below).

```powershell
acde eval notes 'document.querySelector(\"#x\").textContent'   # Windows PowerShell 5.1 only
```

```bat
acde eval notes "document.querySelector(\"#x\").textContent"
```

Code that has only single quotes inside it is written the same way in all three, and passing the code on stdin avoids the question (shown for PowerShell):

```powershell
acde eval notes "document.querySelector('#x').textContent"
'document.querySelector("#x").textContent' | acde eval notes -
```

The same applies to any argument with double quotes, such as `act ... type`. `bin\acde.cmd` is still installed next to `acde.exe` as a fallback (`acde.cmd …`), but PowerShell drops double quotes in the arguments it passes to a `.cmd`.

### inspect and act

`inspect` gives every element a **ref**, such as `w1.18` (element 18 in window `w1`); pass it to `act`.

```sh
$ acde inspect
- window "Notes" [app=notes] [focused] [fullscreen] [w1]
  - heading "Notes" [level=1] [w1.16]
  - form [w1.6]
    - text "Title" [w1.17]
    - textbox "Title": "" [w1.18]
    - text "Email" [w1.19]
    - textbox "Email": "" [w1.20]
    - button "Save" [w1.21]
  - list "Saved notes" [w1.7]
    - listitem [w1.22]
      - text "Buy milk" [w1.22]
  - text "1 note" [w1.8]
  (1 more outside the visible area; scroll, or add offscreen)

$ acde act w1.18 type "Weekly report"
typed, the value is now "Weekly report"

(windows unchanged)
- window "Notes" [app=notes] [focused] [fullscreen] [w1]
  ~ - textbox "Title": "Weekly report" [focused] [w1.18]
  (1 more outside the visible area; scroll, or add offscreen)

$ acde act w1.21 click
clicked 55,202

(windows unchanged)
- window "Notes" [app=notes] [focused] [fullscreen] [w1]
  ~ - textbox "Title": "" [w1.18]
  ~ - button "Save" [focused] [w1.21]
  + - listitem [w1.23]
  + - text "Weekly report" [w1.23]
  ~ - text "2 notes" [w1.8]
  (1 more outside the visible area; scroll, or add offscreen)
```

Without `--find`, the text is always in this English format: one line per window, top first (`- window "Notes" [app=notes] [focused] [w1]`, the desktop is `- desktop`), and under a listed window its elements, indented two spaces per level, as `- role "name": "value" [states] [ref]` (the value only where the element has one). Notes in parentheses say what is left out or unchanged, such as `(empty)`, `(no changes)` and `(windows unchanged)`.

`act` prints what it did on the first line (`clicked 55,202` is the point it clicked, in window coordinates), waits for the page to settle, and then prints the windows and the content of the window again. Where it has listed that window before, it prints only what changed since: `~` for a changed line, `+` for a new one, `-` for one that is gone; `(windows unchanged)` stands for an unchanged window list. So the output of `act` is usually all you need to read before the next step. An element that is scrolled out of view is scrolled into view first, so a ref from `inspect --offscreen` or `query` works wherever the element is on the page.

`act` exits with code 0 when the action was done. When it was not, the reason is the only line and the exit code is 1: `the element is not displayed` (it is `display: none` or hidden by `visibility`), `covered by another element: <div> (27)`, `cannot type into this element`, `element 23 is gone` (see below), `w1 is minimized; act restore on it first` (a click or another pointer action on a minimized window or on an element in it).

A ref stays the same as long as its element lives: moving it, changing its text or attributes, or reordering a list keeps it. When the page replaces the element with a new one (for example by setting `innerHTML`), the new element gets a new ref, and acting on the old one fails with `element N is gone`; take a new `inspect` then.

By default the tree leaves out elements that can't be seen: `display: none`, `aria-hidden`, `inert`, `opacity: 0` and hidden `visibility`. `--all` lists every window that is not marked `[minimized]` in the window list and also keeps the elements hidden by `opacity: 0` (marked `transparent`; they can still be clicked) or by `visibility` (marked `invisible`; they can't); `display: none`, `aria-hidden` and `inert` are always left out.

A window that is off the screen is marked `[minimized]` in the window list: one whose state is `minimized` (after `act w1 minimize`, the app's own `minimize()`, or the desktop's `windows.requestState(id, 'minimized')`), and one the desktop hid with `windows.hide(id)`. Its elements are not listed: `--all` and `--find` skip it, and `--window w1` prints `(empty)` and `(minimized; act restore on it to see its elements)` under its line. Pointer actions on it (`click`, `double`, `right`, `hover`, `scroll`, and `drag` from or onto it) are refused, and `act w1 restore` brings it back. In a desktop session:

```sh
$ acde act w1 minimize
w1 is minimized (the windows changed)

- window "Tools" [app=tools] [minimized] [w1]
- desktop [focused] [fullscreen] [w0]
  - navigation "Apps" [w0.6]
    - button "Tools" [w0.10]

$ acde act w1.10 click
w1 is minimized; act restore on it first

$ acde act w1 restore
w1 is in front (the windows changed)

- window "Tools" [app=tools] [focused] [w1]
  + - heading "Tools" [level=1] [w1.10]
- desktop [fullscreen] [w0]
```

`--find TEXT` looks in every window that is not marked `[minimized]` (or in `--window W`) and prints only the elements whose name or value contains the text (case does not matter). Its output has a format of its own: a line `<window ref> <app id> "<title>":` for each window that has a match (`w0 desktop:` for the desktop), and under it one line per element. An element inside an ancestor that has a name is followed by `in` and the nearest such ancestor; one that has none is followed by nothing:

```sh
$ acde inspect --find milk
w1 notes "Notes":
- text "Buy milk" [w1.22]  in list "Saved notes" [w1.7]

$ acde inspect --find save
w1 notes "Notes":
- button "Save" [w1.21]
- list "Saved notes" [w1.7]
```

When nothing matches it says so on stderr and exits with code 1. Elements scrolled out of view are found only with `--offscreen`; without it, a note under the tree says how many were left out (`(1 more outside the visible area; scroll, or add offscreen)`).

Actions: `click` `double` `right` `hover` `scroll` `type` `settext` `select` `key` `drag` `focus`; a window ref (`w1`) also accepts `close` `minimize` `restore`. `minimize` on a window that cannot be minimized changes nothing, says why and exits with code 1; in a session that runs a single app, on macOS and headless, that is the app's own window: `w1 cannot be minimized: it fills the host window, which only the host window's own controls minimize here`. The argument to `key` looks like `"ctrl+a backspace"`; the argument to `drag` is the target ref. When closing a window ends acdert (the app's window when `acde dev` runs one app), `acde dev` ends with it; `act w1 close` then says so and exits with code 0.

#### Key names

The argument to `key` (and `press()` in tests) is one or more chords separated by spaces; a chord is keys joined by `+`, pressed in order and released in reverse. Keys are physical keys on a US layout. Case does not matter, except that a single capital letter (`A`) adds `shift`:

- modifiers: `ctrl` (`control`), `shift`, `alt`, `super` (`meta`, `win`)
- letters `a` … `z`, digits `0` … `9`, `f1` … `f12`
- `enter` (`return`), `escape` (`esc`), `tab`, `space`, `backspace`, `delete` (`del`), `insert`, `home`, `end`, `pageup`, `pagedown`, `up`, `down`, `left`, `right`, `menu`
- printable characters as they are: `-` `=` `[` `]` `;` `'` `` ` `` `\` `,` `.` `/`, and the shifted ones `!` `@` `#` `$` `%` `^` `&` `*` `(` `)` `_` `+` `{` `}` `|` `:` `"` `<` `>` `?` `~`, which add `shift` themselves (`*` is `shift+8`). `+` alone, or last in a chord (`ctrl++`), is the `+` key
- names for some characters: `plus` (`+`), `multiply`, `asterisk`, `star` (`*`), `minus` (`-`), `divide` (`/`), `period` (`.`), `comma` (`,`); these are the main keyboard keys, not the keypad
- the keypad: `Numpad0` … `Numpad9`, `NumpadAdd`, `NumpadSubtract`, `NumpadMultiply`, `NumpadDivide`, `NumpadDecimal`, `NumpadEnter`
- the DOM `KeyboardEvent.code` names of the other keys, e.g. `KeyA`, `Digit8`, `Minus`, `ArrowUp`, `CapsLock`, `ShiftRight`

The whole argument is checked before anything is pressed: an unknown key fails with `unknown key: …` and presses nothing. The space character is `space` (spaces separate chords). To enter text, use `type` instead.

### query

`inspect` lists what a user can see and use. `query` finds elements by CSS selector whether they are shown or not, and gives each a ref, so it reaches what `inspect` leaves out: an element that is `display: none`, one that is scrolled out of view, and one that has no role, name or value of its own (a plain `<div>`; `inspect` lists what is inside it in its place).

```sh
$ acde query 'form input[type=email]'
1 in w1:
- textbox "Email": "" [w1.20] <input>

$ acde query '[data-testid="menu"] li'
2 in w1:
- generic "Rename" [w1.25] <li> [hidden]
- generic "Delete" [w1.26] <li> [hidden]

$ acde query button
4 in w1:
- button "Save" [focused] [w1.21] <button>
- button "Undo" [transparent] [w1.10] <button> [hidden]
- button [invisible] [w1.24] <button> [hidden]
- button "Load more" [w1.11] <button>

$ acde query nav
nothing in w1 matches "nav"
```

Each line is the element's role, name, value, a heading's level, states and ref, exactly as `inspect` prints them (`- heading "Notes" [level=1] [w1.16] <h1>`), then its tag. `[hidden]` after the tag marks an element that is not visible: it has no size, or is `display: none`, hidden by `visibility`, or transparent, or its window is minimized. The `transparent` and `invisible` marks are the ones `inspect --all` gives: a transparent element still takes clicks, as it does for a user; for an `invisible` or `display: none` one, `act` answers `the element is not displayed` until the page shows it. An element whose role cannot be told is listed as `generic`; the tag says what it is.

The refs work with `act`, like the ones from `inspect`: `acde act w1.20 type "me@example.com"`. `query` searches the focused window; `--window w2` picks another, `--ref w1.6` searches only under that element, and `--limit N` lists at most N elements (1 to 3000, default 600; the first line still counts them all). Finding nothing is not an error: the exit code is 0 either way.

### console and network

```sh
acde console --level errors --follow
acde network --failed
```

`--level` is `log`, `info`, `warn`, `error`, `debug`, or `errors` (`console.error` plus uncaught errors). `--follow` keeps printing new entries.

When a `fetch` in the page rejects with `TypeError: Failed to fetch`, the line of that request in `acde network --failed` says why (a CORS rule, a name that does not resolve, a refused connection):

```sh
$ acde network --failed
   1 GET    ERR https://nonexistent.invalid/  (fetch 158 ms; Failed to connect to host: Failed resolving hostname: failed to lookup address information: nodename nor servname provided, or not known) notes#1048576
```

Entries stay after a page reloads, so errors from before a change are still listed. The first column is the entry's number. `--since reload` lists only what came after `acde dev` last rebuilt and reloaded (everything, if it has not reloaded yet); `--since N` lists entry `N` and later. A reload the page does by itself (`location.reload()`) does not count.

```sh
acde console --level errors --since reload
```

The most recent 5000 entries of each kind are kept.

## Approvals

An app that requires a capability needing the user's approval (`terminal`, `network`, `camera`, `microphone`, `launch`, `slots`, or a shared folder named in `fs.roots`, such as `fs.downloads`) opens no window until the prompt is answered, and nothing answers it by itself (on Windows the host window asks in a dialog; on macOS, on Linux and in a headless session there is no dialog). `acde dev` prints the runtime's line `Notes (notes) waits for the user to allow "fs.downloads" (prompt 1; answer it with acde allow or acde deny, …)`, and `acde webs` lists no page and says what the app waits for. Answer with `acde allow` or `acde deny`:

```sh
$ acde webs
NAME  KIND  APP  WINDOW  TITLE
notes waits for approval of fs.downloads: acde allow (or acde deny)

$ acde permissions
pending:
  1  notes  fs.downloads  (launch)
decisions: none

$ acde allow
allowed notes fs.downloads (prompt 1)

$ acde webs
NAME           KIND  APP    WINDOW   TITLE
notes#1048576  app   notes  1048576  Notes
```

Without arguments, `acde allow` and `acde deny` answer the only waiting prompt. When several wait, they answer none and list them; name one by its id (`acde allow 2`) or by app and capability (`acde allow notes fs.downloads`), or answer them all with `--all`. In a desktop session `acde webs` always lists the desktop's page, so look at `acde permissions` there: an app's prompt is raised when the app is first opened.

Decisions persist per app (in `$XDG_CONFIG_HOME/acde/permissions.json`), so an approval is not asked for again, in this session or later. Approving is the user's decision: when you run these commands for someone, allow only what they asked for or agreed to, and tell them what you allowed.

```sh
$ acde permissions
pending: none
decisions:
  notes  fs.downloads  granted

$ acde revoke notes fs.downloads
revoked notes fs.downloads
```

`acde revoke <app> <capability>` removes a decision. For the rest of this run the capability counts as denied (its calls reject with `code: 'denied'`), and the next run asks again. In a session that runs a single app, an app that has lost a required capability cannot start again: the next reload ends the session with the line `acdert app notes: Notes: "fs.downloads" is denied by the user; acdert app asks for it again the next time it runs` and exit code 1, and the next `acde dev` asks.

If you deny a capability the app requires, the app does not start. In a session that runs a single app, `acde dev` then logs `acdert app notes: Notes: "fs.downloads" is denied by the user; acdert app asks for it again the next time it runs` and exits with code 1; the next `acde dev` of that app asks again (`Notes (notes) was denied "fs.downloads" in an earlier run: asking again`), so a denial never locks you out of your own app. In a desktop the denial stays until it is revoked: the app leaves the app list and opening it rejects with `status: 403`, `code: 'denied'` (see [Desktops](https://docs.dopame.ai/guide/desktop.md#apps)). Which capabilities need approval, and how an app can make one optional, is in [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval).

## Errors

When a command fails, it prints `acde: <reason>` and exits with code 1. If the session has already exited, it says `acde dev <pid> is gone`.

# Coding agents

acde ships a **skill**: instructions and reference files that teach a coding agent (Claude Code, Codex, Cursor, Gemini CLI, and any other that reads the [Agent Skills](https://agentskills.io) format) how to create, run, inspect, and test acde projects. The skill is part of the acde archive, so it always describes the acde you have installed. These docs are generated from the same files.

## Set up with one prompt

Paste this into your agent:

```text
Read https://pkgs.dopame.ai/acde/install.md and follow it to set up acde on this machine.
```

It installs acde, installs the skill for the agent, and reports what is ready and what is missing.

## Install the skill yourself

```sh
acde skills install
```

This links the skill into:

- `~/.agents/skills/acde`, the directory shared by agents that follow the common convention (Codex, Cline, Zed, Warp, Pi, and others);
- the skills directory of every other agent found on this machine, such as `~/.claude/skills/acde` for Claude Code or `~/.cursor/skills/acde` for Cursor.

Each one is a link to the skill inside the acde install, so upgrading acde upgrades the skill.

| Command | What it does |
| --- | --- |
| `acde skills` | Shows where the skill is installed and whether each place is current |
| `acde skills install` | Installs it for every agent found |
| `acde skills install --agent claude-code,cursor` | Installs it for these agents, found or not |
| `acde skills install --dir DIR` | Installs it into `DIR/acde`; for an agent acde does not know, or a project's own skills directory such as `.agents/skills` |
| `acde skills install --copy` | Copies instead of linking; for agents that cannot follow links. Run it again after upgrading acde |
| `acde skills remove` | Removes it from everywhere it was installed (add `--dir DIR` for a directory you chose), and the skills directories `acde skills install` created there once they are empty |
| `acde skills path` | Prints the directory of the skill inside the acde install |

`acde skills install` never replaces a directory named `acde` that is not this skill; it stops and names it.

## Agents without skills

Point the agent at the skill's entry file. For example, in the project's `AGENTS.md`:

```text
This is an acde project. Before working on it, read the file SKILL.md in the directory `acde skills path` prints.
```

The same tools are available over [MCP](https://docs.dopame.ai/guide/mcp.md) for agents that prefer it.

# MCP

`acde mcp` is an [MCP](https://modelcontextprotocol.io) server over stdio. It gives AI agents the [debugging tools](https://docs.dopame.ai/guide/tools.md) and more: an agent can start an `acde dev` session itself, look at the screen, click buttons, read the console, and take screenshots, so it can build and verify your app.

Agents can do all of this with the plain [debugging commands](https://docs.dopame.ai/guide/tools.md) too, which need no setup; the [acde skill](https://docs.dopame.ai/guide/agents.md) teaches them how. Use MCP when your agent works better with tools than with a shell.

## Setup

Claude Code:

```sh
claude mcp add acde -- acde mcp
```

Other clients: the command is `acde mcp`, with no arguments (add `--session <pid>` to pin a particular session).

## Tools

| Tool | What it does |
| --- | --- |
| `doctor` | Checks this machine for `acde dev`, as [`acde doctor`](https://docs.dopame.ai/guide/doctor.md) does; call it first when `start` fails |
| `doctor_fix` | Checks, fixes what acde may fix without asking, and checks again, as `acde doctor --fix` does. The fixes that download, install or stop something it only names: the user runs `acde doctor --fix` in a terminal (it asks), or agrees to `acde doctor --fix --yes`. Its `dir` must be inside the working directory |
| `sessions` | Lists running `acde dev` sessions; can pin one |
| `start` / `stop` / `logs` | Starts its own `acde dev` session (for the project in the working directory by default), stops it, reads its output |
| `webs` | Lists pages; when an app waits for an approval instead, says so |
| `permissions` / `answer` / `revoke` | Lists the approval prompts that wait and the decisions made, allows or denies a waiting prompt, takes back a decision; see [Approvals](https://docs.dopame.ai/guide/tools.md#approvals) |
| `snapshot` | The screen as text: windows and the elements of the focused window, each with a ref |
| `act` / `run` | Performs one action on a ref / several in sequence, and reports what changed |
| `open` | Opens an app and waits for its window |
| `query` | Finds elements by CSS selector, hidden ones too; the refs work with `act` |
| `wait_for` | Waits for some text to appear (or disappear) |
| `screenshot` | Screenshot of one window or the whole screen |
| `eval` | Runs JS in a page |
| `console` / `network` | The pages' logs and requests |
| `emulate` | Switches light/dark mode and reduced motion |
| `choose_folder` / `choose_files` / `choose_save_file` | Answers the page's next file picker in advance |
| `route` / `unroute` | Fakes responses to the page's requests, or makes them fail |
| `clipboard` | Reads and writes the clipboard |
| `input` | Sends raw mouse and keyboard events to a page, at page coordinates |
| `clock` | Takes over a page's time: installs a fake clock, pauses it, moves it forward |
| `dialog` | Answers the page's next `alert` / `confirm` / `prompt` in advance, and lists the dialogs it showed |
| `resize` | Resizes a window so that its page has the given size |

Which session is used: the pinned one; otherwise the one `start` launched; otherwise one picked by the working directory.

An app that requires a capability the user must approve opens no window until its prompt is answered. `start` and `webs` then answer an empty table and a line per prompt, `notes waits for approval of fs.downloads: the answer tool allows or denies it`. `answer` takes `allow` (true or false). To allow, it must name the `app` and the `capability` that `permissions` lists, so the call states what is granted; to deny, the `prompt` id or the `app` and `capability` will do, and neither is needed when only one prompt waits. It stands in for the user's own answer, so the tool is marked as an action that needs confirmation: allow only what the user asked for or agreed to.

Closing the only window of a session that runs a single app (`act` with `close` on `w1`) ends that session, by design. The call succeeds and its answer says so, `closed w1; acdert exited with it, so acde dev 4242 ended`. The next call fails and says that the session stopped (`the acde dev started here (pid 4242) stopped; last output: …` for a session `start` ran, `acde dev 4242 stopped; no acde dev is running (…)` for one started elsewhere). Run `start` again to go on. Any other action during which the runtime goes away fails with `acdert closed the connection`; so does a `run` whose steps close that window, since the answer to its steps is lost, so close it with `act`.

`input`, `clock`, `dialog` and `resize` do for an agent what `app.mouse` / `app.keyboard`, `app.clock`, `app.answerDialog` and `app.resize` do in a test; see [Time, dialogs and page setup](https://docs.dopame.ai/guide/testing.md#time-dialogs-and-page-setup). `clock` takes `action` (`install`, `pause_at`, `fast_forward`, `run_for`, `resume`, `set_fixed_time`, `set_system_time`, `state`) with a `time` (an ISO string or milliseconds since 1970) or a `duration` (milliseconds, `"mm:ss"` or `"hh:mm:ss"`). `dialog` without `accept` or `text` only lists.

In a session with windows, `clipboard` touches **your system clipboard**, so the agent must pass `system: true` explicitly, and the tool is marked as an action that needs confirmation. Headless sessions have their own clipboard.

When the server's stdin closes or it receives a signal, it stops the `acde dev` session that `start` launched.

# Testing

`acde test` tests your app in the real runtime: each test gets a fresh, isolated `acde dev` session, and a Playwright-like API finds elements, clicks, types, asserts, and compares screenshots. Requires Bun, even when the project itself runs on Node.js.

## A first test

Test files are named `*.e2e.ts` (or `.tsx`, `.js`, `.mjs`, `.mts`) and can live anywhere in the project:

```ts
// e2e/tasks.e2e.ts
import { test, expect } from 'acde/test'

test('adds a task', async ({ app }) => {
  await app!.getByRole('textbox', { name: 'New task' }).fill('Buy milk')
  await app!.getByRole('button', { name: 'Add' }).click()
  await expect(app!.getByRole('listitem')).toHaveCount(1)
})

test('starts empty again', async ({ app }) => {
  await expect(app!.getByRole('listitem')).toHaveCount(0)
})
```

```sh
acde test
```

Plain `bun test` does not match `*.e2e.*`, so unit tests and end-to-end tests stay out of each other's way. `acde test` resolves `acde/test` and `acde/driver` to the acde that is running it, so the project does not need to install anything.

## Fixtures

The test function receives:

| Name | What it is |
| --- | --- |
| `app` | For an app project, its window (`AppWindow`); for a desktop project, `null` |
| `acde` | The whole session (`Acde`): open apps, take screenshots, emulate, fake requests, and more |
| `home` | This test's temporary `HOME` |
| `settings` | The settings for this run |

## Isolation

Each test gets:

- Temporary `HOME` and `XDG_*` directories, and in-memory storage only;
- A 1280 × 800 screen, light mode, reduced motion, and no autostart items;
- Headless by default (`--headed` to watch in a window), with a 60-second timeout per test (`--timeout`); the time the session takes to start counts. Headless still needs a GPU, so Linux CI machines without one can't run tests; see [Platform support](https://docs.dopame.ai/reference/platforms.md).

Builds go into `.acde/test`, results into `.acde/test-results`.

## Locators

The same locators as Playwright, matched against the **semantic tree** (the accessibility tree):

```ts
app.getByRole('button', { name: 'Save' })
app.getByText('Saved')
app.getByLabel('Email')
app.getByPlaceholder('Search')
app.getByTitle('Close')
app.getByAltText('Avatar')
app.getByTestId('submit')          // data-testid
app.locator('ul.tasks > li')       // CSS selector
app.getByRole('listitem').filter({ hasText: 'Milk' }).first()
app.getByRole('listitem').filter({ has: app.getByRole('checkbox', { checked: true }) })
app.getByRole('button', { name: 'Save' }).or(app.getByRole('button', { name: 'Retry' }))
app.locator('li').and(app.getByText('Milk'))
```

Locators are lazy: they are resolved again against the latest tree every time they are used. Actions require **exactly one** match; with several, they fail instead of guessing.

`filter` takes `hasText`, `hasNotText`, `has` and `hasNot` (another locator, looked for inside each element). `or` matches what either locator matches, in document order; `and` what both match.

A CSS locator (`locator`, `getByTestId`, `getByPlaceholder`, …) also matches elements that are not rendered, as in Playwright: `toHaveCount` counts them, `toBeVisible` / `toBeHidden` / `isVisible()` / `waitFor({ state })` tell whether an element is rendered, and actions wait until it is. Elements found through the semantic tree (`getByRole`, `getByText`, `getByLabel`) are always rendered ones.

## Actions

```ts
await locator.click()
await locator.dblclick()
await locator.hover()
await locator.fill('text')       // replaces
await locator.type('text')       // appends
await locator.clear()
await locator.press('ctrl+a backspace') // key names: see "Key names" in Debugging
await locator.selectOption('beta')
await locator.check() / uncheck() / setChecked(true)
await locator.dragTo(other)
await locator.scroll(400)
```

`click`, `fill`, and similar actions wait for the element to be enabled (not `disabled`), and retry until the timeout when they fail. The keys `press` takes are listed under [Key names](https://docs.dopame.ai/guide/tools.md#key-names).

`click`, `dblclick` and `hover` take `modifiers`, the keys held meanwhile: `Shift`, `Control`, `Alt`, `Meta`, or `ControlOrMeta`, which is `Control` on every system because pages see a Linux environment everywhere (see [Web platform support](https://docs.dopame.ai/reference/web.md)).

```ts
await locator.click({ modifiers: ['Shift'] })
const size = await locator.evaluate((element, unit) => element.getBoundingClientRect().width + unit, 'px')
```

`locator.evaluate(fn, arg)` runs a function in the page with the element and one JSON argument, and returns its JSON result.

For input that is not aimed at one element, `app.mouse` and `app.keyboard` send raw events at page coordinates (CSS pixels, as `getBoundingClientRect()` gives them):

```ts
await app.mouse.move(40, 120)
await app.mouse.down()
await app.mouse.move(240, 120, { steps: 8 })   // a drag, eight moves a frame apart
await app.mouse.up()
await app.mouse.click(300, 200, { button: 'right' })
await app.mouse.wheel(0, 400)

await app.keyboard.press('Control+a')
await app.keyboard.type('Hello')               // key presses; characters without a key go in as text
await app.keyboard.insertText('你好')           // as the input method commits it
await app.keyboard.down('Shift')
await app.keyboard.up('Shift')
```

## Assertions

```ts
await expect(locator).toBeVisible()
await expect(locator).toHaveText('Done')
await expect(locator).toContainText('Done')
await expect(locator).toHaveValue('42')
await expect(locator).toHaveCount(3)
await expect(locator).toBeChecked()
await expect(locator).toBeDisabled()
await expect(locator).toBeFocused()
await expect(locator).toHaveAttribute('aria-expanded', 'true')
await expect(locator).not.toBeVisible()

await expect(locator).toHaveClass(/active/)
await expect(locator).toHaveCSS('color', 'rgb(255, 0, 0)')    // the computed style
await expect(locator).toHaveJSProperty('checked', true)
await expect(locator).toBeEmpty()
await expect(locator).toBeEditable()
await expect(locator).toBeInViewport({ ratio: 0.5 })

await expect(app).toHaveTitle('Notes')
await expect(app).toBeOpen()
```

`toHaveText` and `toContainText` compare the element's text content, as in Playwright: the text inside it, whitespace collapsed, not its accessible name. An `<output aria-label="Display">18</output>` has the text `18`; locators such as `getByText` and `getByRole(…, { name })` match the accessible name (`Display`). `locator.textContent()` reads the text content, `locator.name()` the accessible name.

UI assertions retry until the timeout (5 seconds by default). `expect` on any other value is the `expect` from `bun:test`.

`expect.poll` retries a `bun:test` matcher on a value the test reads itself, until it passes or the timeout runs out. `expect.soft` records a failure and lets the test go on; the test fails at its end with every soft failure listed.

```ts
await expect.poll(() => app.evaluate<number>('window.saved'), { timeout: 2000 }).toBe(3)
await expect.soft(app.getByRole('heading')).toHaveText('Notes')
expect.soft(total).toBe(42)
```

## Screenshots

```ts
await expect(app).toHaveScreenshot()
await expect(app.getByRole('textbox')).toHaveScreenshot('field', { maxDiffPixels: 20, mask: [app.getByTestId('clock')] })
```

- Baselines live next to the test file in `__screenshots__/<file name>/<name>-<platform>.png`. If there is no baseline, one is written; if the `CI` environment variable is set, that is an error instead.
- Screenshots are taken until two in a row are identical, and only then compared; on a mismatch, it keeps retaking until the timeout.
- On failure, three images, `-actual`, `-expected`, and `-diff`, are written to the results directory.
- `acde test -u` rewrites the baselines.
- Options: `maxDiffPixels`, `maxDiffPixelRatio`, `threshold` (default 0.2), `mask`, `timeout`.

## Network, file pickers, clipboard

```ts
// Fake responses
await app.route('/api/todos', { json: [{ id: 1, title: 'mocked' }] })
await app.route('**/avatar.png', { abort: true })

// Wait for a request or a log entry (call first, then trigger)
const request = app.waitForRequest('/api/save', { method: 'POST' })
await app.getByRole('button', { name: 'Save' }).click()
await request

// Answer file pickers in advance
await acde.chooseFiles(['/tmp/a.txt'])
await acde.chooseFolder('/tmp/project')
await acde.chooseSaveFile('/tmp/out.md')

// Dark mode
await acde.emulate({ colorScheme: 'dark' })

// Clipboard (headless sessions have their own)
await acde.setClipboard('hello')
```

## Time, dialogs and page setup

`app.clock` takes over the page's time, so a test of a timer does not wait for it:

```ts
await app.clock.install({ time: '2026-01-01T09:00:00Z' })   // Date, performance.now, timers and animation frames
await app.clock.fastForward('25:00')                         // jump ahead; each timer that is due fires once
await app.clock.runFor(1000)                                 // step ahead; every timer fires at its own time
await app.clock.pauseAt('2026-01-01T10:00:00Z')
await app.clock.resume()
await app.clock.setFixedTime(0)                              // Date stands still; timers go on
await app.clock.setSystemTime('2030-06-01')                  // moves Date only
```

Times are milliseconds since 1970, a `Date` or a date string; durations are milliseconds, `"mm:ss"` or `"hh:mm:ss"`. An installed clock stays until the page reloads. CSS animations and transitions keep running on real time.

acdert has no dialog for the user to click: an `alert` is drawn in the window, `confirm` answers false and `prompt` null. A test answers the next one in advance:

```ts
await app.answerDialog({ accept: true })              // the next confirm answers true
await app.answerDialog({ text: 'Untitled' })          // the next prompt answers this text
const shown = app.waitForDialog({ type: 'confirm' })  // call first, then trigger
await app.getByRole('button', { name: 'Delete' }).click()
expect((await shown).message).toBe('Delete this note?')
await app.dialogs()                                   // every dialog the page showed, and how it was answered
```

To start a test from a prepared page:

```ts
test('opens the saved draft', { size: [480, 640], localStorage: { draft: 'Hello' } }, async ({ app }) => {
  await expect(app!.getByRole('textbox')).toHaveValue('Hello')
})
```

The options come second or third (`test(name, options, body)` or `test(name, body, options)`): `timeout`, `size` (the page's width and height) and `localStorage` (written before the page loads). They do what these calls do inside a test:

```ts
await app.seedLocalStorage({ draft: 'Hello' })   // writes the entries, then reloads the page
await app.resize(480, 640)                        // the page's size, without the title bar
await app.addInitScript('window.testing = true')  // runs before the page's own scripts, on every load
await app.reload()
```

`size` and `localStorage` need the `app` fixture, so they work in an app project, not with `--desktop`.

## Approvals

Some capabilities need the user's approval before the app gets them (see [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval)). Every test starts with an empty home, so nothing is approved yet, and no prompt is answered by itself: an app that requires such a capability opens no window until the test answers. Answer first, then use `app`:

```ts
import { expect, test } from 'acde/test'

test('the app gets Downloads once the user allows it', async ({ app, acde }) => {
  await acde.allow({ capability: 'fs.downloads' })
  const roots = await app!.evaluate<{ id: string }[]>(`import('acde:fs').then((m) => m.fs.roots())`)
  expect(roots.map((root) => root.id)).toEqual(['private', 'downloads'])
})
```

`acde.allow()` and `acde.deny()` wait for a matching prompt (`{ app, capability }`, both optional) and answer it; `acde.permissions()` lists what waits and what was decided; `acde.revoke(app, capability)` takes a decision back. To test how the app behaves when the user says no, make the capability optional in the config and `deny` the prompt that `request()` raises; denying a required capability means the app does not start.

## Failures

A failed test leaves these in `.acde/test-results/<file>/<test>/`:

`error.txt` `output.log` `screen.png` `snapshot.txt` `console.txt` `network.txt` `trace.txt`

A test that runs out of time fails with `TimeoutError: the test did not finish within <ms> ms (its timeout: --timeout, or the one given to test())` and leaves the same files, taken at that moment.

A test whose session does not start has no screen to save: it leaves `error.txt` and `output.log`, the whole output of that test's `acde dev`. The error says how far the start got, then quotes the last 40 lines of that output (an app that cannot start says why there, for example `Notes needs "clock" (service not running)`):

| The error starts with | What happened |
| --- | --- |
| `acde dev exited (<code>) before it was ready:` | `acde dev` ended with that exit code: the build failed, or acdert refused the app |
| `acde dev (pid <pid>) did not register a session within <n> s in <dir>`, then `no session yet: its build did not finish, or acdert did not start listening; last output:` | The build or the start of acdert took longer than the test's timeout allows |
| `acde dev did not start within <n> s:`, then `acdert runs and answers, but no window appeared (pages: 0, windows: 0) and no approval prompt waits; last output:` | acdert runs, but the app opened no window |

With `--trace`, every test leaves a `trace.html`: each action and assertion, with its duration and result, and a full-screen screenshot after each step.

With `--video`, a failing test also leaves `video.png`, an animated PNG of the screen (four frames a second, the last 600 that differ); `--video=on` keeps one for every test. With `--retries`, the directory holds what the last attempt left.

## Commands

```sh
acde test                        # all *.e2e.* in the project
acde test e2e/tasks.e2e.ts       # specific files
acde test -t "adds"              # only tests whose names match this regular expression
acde test --headed               # watch in a window
acde test --desktop dopame       # run the app in the dopame desktop
acde test --bail --timeout 30000
acde test --trace
acde test -u                     # update screenshot baselines
acde test --workers 2            # two files at a time
acde test --retries 1 --video    # run a failing test once more; keep a video of failing tests
```

Several files run at once: half the machine's cores, at most 4, and one at a time with `--headed` or `--bail` (`--workers` sets it). Each worker builds into its own directory (`.acde/test`, `.acde/test-2`, …). A test that fails is run again `--retries` times, each time on a fresh session with its own timeout; when a later attempt passes, the test passes and a line says `passed on attempt 2 of 2 (flaky)`.

With `-t`, a file in which no test matches is skipped and does not count as failed (`acde test: e2e/approval.e2e.ts: no test matches -t "saves", skipped`); if no test matches in any file, `acde test` prints `acde test: no test matches -t "<pattern>" in <n> files` and exits with code 1.

Each file prints the output of its own `bun test` run as it goes; when several run at once, a file's output is printed in one piece when the file ends. The run ends with two summary lines, one that counts tests and one that counts files:

```text
acde test: 5 tests ran: 4 passed, 1 failed, 1 not run (skipped, todo, or not matched by -t)
acde test: 2 files, 1 passed, 1 failed: e2e/notes.e2e.ts
  what the failing tests left: /path/to/notes/.acde/test-results
```

- The first line counts the tests of the files that ran: how many ran, passed and failed, and, when there are any, how many did not run (`test.skip`, `test.todo`, and tests that `-t` left out). The numbers come from the report `bun test` writes for each file. A file that left no report (it failed to load, or its run was killed) is named instead of counted: `; not counted: e2e/broken.e2e.ts (bun test left no report: the file did not load, or its run was killed)`.
- The second line counts the files that ran, **not tests**: a file passes when all its tests did. It names the files that failed, and adds `, <n> skipped (no test matches -t)` and `, <n> not run (--bail)` when that applies. The indented line under it appears when a failing test left files.

The exit code is 0 when nothing failed and 1 otherwise.

## Editor types

`acde/test` exports the types of everything it hands you, so helpers can be typed: `Fixtures` (the test body's argument), `AppWindow` (the `app` fixture), `Locator`, `Acde`, and the option and result types listed in the [Testing API](https://docs.dopame.ai/reference/testing.md).

```ts
import { test, expect, type AppWindow, type Locator } from 'acde/test'

async function enter(app: AppWindow, keys: string[]): Promise<Locator> {
  for (const key of keys) await app.getByRole('button', { name: key }).click()
  return app.locator('#display')
}

test('adds', async ({ app }) => {
  await expect(await enter(app!, ['1', '+', '2', '='])).toHaveText('3')
})
```

`acde test` resolves `acde/test` on its own at run time, but your editor does not know where it is. For now, add `paths` to the project's `tsconfig.json` pointing at the type declarations in the install directory, with the absolute path of your home directory (`tsconfig.json` does not expand `~` or `%USERPROFILE%`):

```jsonc
{
  "compilerOptions": {
    "skipLibCheck": true,
    "paths": {
      "acde/test": ["/home/me/.acde/current/lib/acde/dist/types/e2e/index.d.ts"],
      "acde/driver": ["/home/me/.acde/current/lib/acde/dist/types/driver/index.d.ts"]
      // Windows: "C:/Users/me/.acde/current/lib/acde/dist/types/e2e/index.d.ts"
    }
  }
}
```

`acde test` reads the same `paths` and replaces these two entries with its own, so they do not change how tests run. A separate types package will follow.

# Local install

`acde dev` hands your app to the runtime only temporarily. To keep the app in the Dopame desktop on this machine:

```sh
acde install
```

This runs `acde build`, then installs the package into `$XDG_DATA_HOME/acde/packages/<id>` (by default `~/.local/share/acde/packages/<id>`, on Windows `%USERPROFILE%\.local\share\acde\packages\<id>`). It copies to a temporary directory first and then swaps the whole directory in, so you never end up with half a package. A handwritten package (no config, with its own `acde` manifest in `package.json`) is installed as a symlink to the project.

Once installed, the next session you start (and `acde dev --desktop dopame`) will see it.

## Package lookup

In this order; for a given id, the first one found wins:

1. Directories in `ACDE_PATH` (this is how `acde dev` hands over its builds);
2. `$XDG_DATA_HOME/acde/packages/*`;
3. `$XDG_DATA_DIRS/acde/packages/*` (system-wide installs).

## Uninstall

Delete `$XDG_DATA_HOME/acde/packages/<id>`.

## Publishing

An app store and `acde publish` are still in the works. For now, distributing an app means distributing the built package directory (`.acde/`); put it in any of the locations above.

# CLI

```text
acde <command> [args]
```

On error, acde prints one line, `acde: <reason>`, and exits with code 1. A wrong argument (an action `act` does not know, a level `console` does not know, …) is answered with one line that names what is wrong and the `acde <command> --help` to read, such as `acde: console: --level loud: one of log, info, warn, error, debug, errors (acde console --help)`; the full usage is printed only by `acde` with no command.

`acde --version` (or `-v`) prints the version of acde on the first line, then the SDK version and contract level it was built with, and the acdert it finds (`ACDERT`, the one installed next to acde, then PATH) with that runtime's version and contract level. `acde --help` (or `-h`) prints the usage; `acde <command> --help` and `acde help <command>` print that command only. An unknown command or argument prints one line that says what is wrong and which `--help` to read, and exits with code 1. Color follows `NO_COLOR`.

## Setup

### acde doctor

```text
acde doctor [dir] [--json] [--online] [--fix [--yes]]
```

Checks what `acde dev` and `acde test` need on this machine: acde on PATH, Bun and Node.js, acdert (found, runs, runs the contract level this acde builds, is the release this acde pairs with), the runtime's own checks (`acdert doctor`: its host files, the GPU, and on Linux the display), running `acde dev` sessions and the approvals they wait for, the project in `dir` (default: the current directory; `acde check`, this platform, its dependencies, `.acde/` in `.gitignore`), and the acde skill for coding agents. See [Check the setup](https://docs.dopame.ai/guide/doctor.md).

| Option | Description |
| --- | --- |
| `--json` | One JSON object instead of lines: `{"ok": …, "checks": [{"id", "title", "status", "summary", "fix", "repair"}]}`; with `--fix` also `"fixed"` |
| `--online` | Also ask `pkgs.dopame.ai` (or `ACDE_DIST`) whether a newer acde is out |
| `--fix` | After the checks, fix what acde can: some fixes right away, the others after asking; then check again. See [Fix what it can](https://docs.dopame.ai/guide/doctor.md#fix-what-it-can) |
| `--yes` | With `--fix`: do the fixes that ask first without asking |

It prints one line per check, `<status> <check>: <what it found>`, with `fix: …` on the next line for a problem, and a last line that counts errors and warnings. The status is `ok`, `warn`, `error` or `skip` (not checked: no project here, or an earlier check failed). It exits with code 1 when a check is an error, else 0. A `dir` that holds no acde project is an error.

With `--fix`, after the report it prints `fixing: <what>`, the output of what it runs, and `fixed: <what>` or `failed: <what>: <why>` for each fix, `skipped: <what>` for one that was not allowed, and then `acde doctor: after fixing:` and the checks again; the exit code follows the second run. When nothing can be fixed it says `acde doctor: nothing here it can fix; the fix lines say what to do`. `--yes` without `--fix` is an error.

### acde new

```text
acde new [dir] [--template T] [--id ID] [--label NAME] [--backend] [--install] [--git] [--pm PM] [--yes]
```

Creates a project. In a terminal, it asks for whatever is missing; with `--yes`, or outside a terminal, it asks nothing (then `dir` is required, the template defaults to `html`, and no dependencies are installed and no repository is created).

| Option | Description |
| --- | --- |
| `--template` | `html` `desktop` `react` `vue` `svelte` `solid` `preact` `vanilla` `next` `nuxt` `sveltekit` `astro` |
| `--id` / `--label` | App id and display name |
| `--backend` | Include a backend (`html` only) |
| `--install` | Install dependencies |
| `--git` | `git init` and make the first commit (if a git user name and email are configured) |

### acde check

```text
acde check [dir] [--platform windows|macos|linux]
```

Checks the config (id, entry, icon, service modules, framework) and the manifest rules of the SDK, or the manifest and entry files of a handwritten package, and the `acde:` imports against the manifest. It prints `error:`, `warning:` and `note:` lines on stderr and exits with code 1 only when there is an error. A `note:` marks an import that the check lets pass but cannot verify, the namespace of a [desktop service](https://docs.dopame.ai/guide/services.md#call-it) that is not the service's own name: `note: src/main.js:1: app "notes": acde:timer resolves only if the service Notes lists ("clock") provides the "timer" namespace`.

`--platform` adds a check of the app's declared capabilities against what that platform has, once for each way of running an app there (`desktop` and `standalone`, on Linux also `session`):

- A required capability that the platform lacks is an error: `error: windows (desktop): app "notes" requires network, which this mode lacks`.
- An optional capability that it lacks is a note, and no error: `note: windows (desktop): app "notes" runs without optional camera, which this mode lacks`.
- When no required capability is missing, the last line is `ok: linux (session, desktop, standalone): every required capability is there`.

### acde build

```text
acde build [dir] [--out DIR]
```

Builds into `DIR` (default `.acde`). A relative `--out` is resolved against the project being built. The `acde:` imports are checked first, as in `acde check` (an error stops the build, a `note:` is printed), and the manifest of the output is checked again.

### acde install

```text
acde install [dir] [--out DIR]
```

Builds, then installs into `$XDG_DATA_HOME/acde/packages/<id>`; without `XDG_DATA_HOME`, `~/.local/share/acde/packages/<id>` (on Windows `%USERPROFILE%\.local\share\acde\packages\<id>`). See [Local install](https://docs.dopame.ai/guide/install.md).

### acde dev

```text
acde dev [dir...] [--out DIR] [--app ID] [--desktop ID|DIR] [--headless]
```

Builds, starts acdert, and rebuilds and reloads on changes. See [acde dev](https://docs.dopame.ai/guide/dev.md).

## Running sessions

These work with a running `acde dev` session, and all of them accept `--session <pid>`. A `<web>` is one page: a web name from `acde webs`, an app id, or `desktop`; a `<ref>` is an element id from `acde inspect` or `acde query`, such as `w1.12`, or a window, such as `w1`. See [Debugging](https://docs.dopame.ai/guide/tools.md).

| Command | Description |
| --- | --- |
| `acde webs` | Lists pages |
| `acde eval <web> <code\|->` | Runs code in a page and prints JSON |
| `acde shot <web> [-o FILE]` | Window screenshot, default `./<web>.png` |
| `acde screen [-o FILE]` | Full-screen screenshot, default `./screen.png` |
| `acde inspect [--window W] [--find TEXT] [--all] [--offscreen]` | The screen as text |
| `acde query <selector> [--window W] [--ref REF] [--limit N]` | The elements a CSS selector matches, each with a ref |
| `acde act <ref> <action> [arg]` | Performs an action on a ref |
| `acde console [--web W] [--level L] [--since S] [--follow]` | Page logs and errors; `--since reload` or `--since N` |
| `acde network [--web W] [--failed] [--since S] [--follow]` | Page requests; `--since reload` or `--since N` |
| `acde permissions` | The approval prompts that wait and the decisions made |
| `acde allow [<prompt id> \| <app> <capability>] [--all]` | Allows a waiting approval prompt |
| `acde deny [<prompt id> \| <app> <capability>] [--all]` | Denies a waiting approval prompt |
| `acde revoke <app> <capability>` | Takes back a decision |
| `acde stop` | Ends the session and its acdert; see [Stopping](https://docs.dopame.ai/guide/dev.md#stopping) |
| `acde mcp [--session PID]` | MCP server over stdio; see [MCP](https://docs.dopame.ai/guide/mcp.md) |

| Option | Description |
| --- | --- |
| `--window` | `inspect`, `query`: this window (`w1`) instead of the focused one |
| `--ref` | `query`: search only under this element (`w1.12`) |
| `--limit` | `query`: list at most this many elements (1 to 3000, default 600) |
| `--all` | `inspect`: every window that is not marked `[minimized]`, and elements hidden by `opacity: 0` or `visibility`. `allow`, `deny`: every waiting prompt |

`acde query` prints `N in <window>:` and one line per element, or `nothing in <window> matches "<selector>"`; both exit with code 0. `acde act` prints what it did and what changed, and exits with code 1 when the action was not done (the reason is then the only line).

`acde permissions` prints two blocks and exits with code 0:

```text
pending:
  2  notes  fs.documents  (launch)
decisions:
  notes  fs.downloads  granted
```

A pending line is `<prompt id>  <app>  <capability>  (<reason>)`, where the reason is `launch` (asked before the app starts) or `request` (asked by the running app); a decision line is `<app>  <capability>  <granted|denied>`. An empty block is `pending: none` or `decisions: none`.

`acde allow` and `acde deny` answer prompts that wait now. Without arguments they answer the only waiting prompt; when several wait they answer none, list them, and exit with code 1. `<prompt id>` names one prompt, `<app> <capability>` the prompt of that app for that capability, and `--all` every waiting prompt. Each answered prompt prints `allowed <app> <capability> (prompt <id>)` or `denied <app> <capability> (prompt <id>)`. When nothing waits, or nothing matches, they print one line that says so (`acde: no approval prompt is waiting`, `acde: no approval prompt 5 is waiting (waiting: 2)`) and exit with code 1.

`acde revoke <app> <capability>` prints `revoked <app> <capability>`; when there is no such decision it says so and exits with code 1.

When no page runs because an app waits for an approval, `acde webs` prints, after the empty table, one line per prompt: `<app> waits for approval of <capability>: acde allow (or acde deny)`. See [Approvals](https://docs.dopame.ai/guide/tools.md#approvals).

# Manifest

The runtime only understands **packages**: a directory whose `package.json` has an `acde` field holding the manifest. `acde build` generates it from your config; you can also write it by hand.

```json
{
  "name": "my-pkg",
  "acde": {
    "apiLevel": 1,
    "desktops": [{ "id": "dopame", "name": "Dopame", "entry": "desktop/index.html", "services": ["assistant"] }],
    "apps": [{ "id": "term", "label": "Terminal", "icon": "term", "entry": "/app/term/index.html", "capabilities": { "terminal": true } }],
    "assets": { "/app/term/": ["apps/term/web"], "/desktop/dopame/": ["desktop"] },
    "services": [{ "name": "assistant", "module": "services/assistant.js" }]
  }
}
```

There is a single manifest validator: the runtime and `acde check` / `acde build` run the same code (`@dopame/acde-api/manifest`). `acde check <dir>` checks a handwritten package.

## PackageManifest

| Field | Description |
| --- | --- |
| `apiLevel` | The contract level the package is built for, a positive integer; required. See [Contract level](#contract-level) |
| `desktops` | List of desktops |
| `apps` | List of apps. In a package that has a desktop they are system apps |
| `assets` | Same-origin URL prefix (`/…/`) → list of directories in the package |
| `services` | `{name, module}`: service name and module file. A name cannot be that of a system module or capability |

## Contract level

`apiLevel` says which version of the contract between packages and the runtime a package follows. The current level is 1 (`API_LEVEL` in `@dopame/acde-api`; `acde --version` and `acdert --version` print theirs). The runtime loads only packages of its own level:

| Package | What the runtime and `acde check` say |
| --- | --- |
| No `apiLevel` (built before contract levels) | `no acde.apiLevel: a package built before contract levels; rebuild it with the current acde (level 1)` |
| Another level | `acde.apiLevel 2: needs level 2, runtime is level 1` |

A package the runtime refuses is not in the app list or the desktop list. Rebuild it with the current `acde`.

## DesktopManifest

| Field | Description |
| --- | --- |
| `id` / `name` / `description` | |
| `entry` | The desktop page: the path of an HTML file in the package (`desktop/index.html`), not a URL |
| `services` | The services it uses: a name, or `{name, modules}` where `modules` lists the shell modules the service may get from `ctx.import()` (see [Service API](https://docs.dopame.ai/reference/service.md)) |
| `heapMb` | Defaults to 1024, minimum 32 |

## AppManifest

| Field | Description |
| --- | --- |
| `id` | `[\w-]+`, required. The runtime accepts this; a config only allows `[a-z0-9][a-z0-9-]*` (see [acde.config.jsonc](https://docs.dopame.ai/reference/config.md#appconfig)), so the looser rule matters only for a handwritten package |
| `label` | Required |
| `icon` | An icon name, or a URL under assets ending in `.svg` / `.png`; required |
| `entry` | A URL starting with `/`, required. HTML or a module; a trailing `/` means the page is rendered by the backend (requires `backend`) |
| `capabilities` | System capabilities; see below |
| `optional` | Names from `capabilities` the app can run without |
| `services` | Names of the desktop services the app uses |
| `heapMb` | Defaults to 256, minimum 32 |
| `size` | `[width, height]`, defaults to 800 × 600 |
| `multiple` | Defaults to `false` |
| `frame` | Defaults to `true` |
| `mimeTypes` | File types the app can open: `type/subtype` or `type/*` |
| `schemes` | URL schemes of the links the app can open: lowercase, without the colon, not `file` |
| `requests` | Request kinds the app accepts from other apps: lowercase words, not `open-file` or `open-link` |
| `backend` | `{entry, port?}`: `entry` is a `.js` / `.mjs` URL under assets; `port` defaults to 3000 |

## Capabilities

| Key | Value | Grants | Needs the user's approval |
| --- | --- | --- | --- |
| `fs` | `true` \| `{roots: string[]}` | `acde:fs`: the private folder and picked folders; `roots` names shared places (`desktop`, `documents`, `downloads`, `music`, `pictures`, `videos`) | Each place in `roots` |
| `terminal` | `true` | `acde:terminal` | Yes |
| `network` | `true` | `acde:network` | Yes |
| `office` | `true` | `acde:office` | |
| `launch` | `true` | `start` in `acde:launch` | Yes |
| `slots` | `true` | `embed` in `acde:launch`: native programs embedded in the app's window | Yes |
| `open` | `true` \| `string[]` | Opening (these) apps with `acde:open` | |
| `openFiles` | `true` | `acde:openPath`, `acde:handlers`, and `open(request)` without a target app | |
| `camera` / `microphone` | `true` | `getUserMedia()` video / audio | Yes |
| `windows` `packages` `session` `desktops` `inspect` `desktop` `setDefault` `permissions` | `true` | The shell module of that name. System apps only: an error in any other package | |

Any other key is an error: desktop services go in `services`. System apps are never asked for approval.

Everything in `capabilities` and `services` is required unless `optional` lists it (`optional` takes names from `capabilities` only). An app with a required item that is missing here (unsupported on the platform, denied by the user, service not running) is left out of the app list and refuses to start, for example with `Notes needs "network" (unsupported on this platform)`; a denial has a sentence of its own, `Notes: "terminal" is denied by the user` (see [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval)).

## URLs

- Pages have the origin `http://acde.local`.
- An app's files are served at `/app/<id>/` and also mounted at `/`; a desktop is at `/desktop/<id>/`.

# acde: modules

Every module has both named exports and a default export:

```js
import { fs } from 'acde:fs'
import fs from 'acde:fs'
```

Types are in `@dopame/acde-api`: `@dopame/acde-api/app` declares the modules an app can import, `@dopame/acde-api/shell` adds the shell modules, and the package root declares all of them. For how capabilities are requested and approved, see [Capabilities](https://docs.dopame.ai/guide/capabilities.md).

Who can import what. "App" is an app of its own package; a "system app" ships in a desktop's package (the `apps` of a desktop config). A name in a cell is the capability the app must declare:

| Module | App | System app | Desktop page |
| --- | --- | --- | --- |
| `acde:window` | ✓ | ✓ | |
| `acde:capabilities` | ✓ | ✓ | ✓ |
| `acde:apps` | ✓ | ✓ | ✓ |
| `acde:open` | ✓ (opening an app needs `open`) | ✓ (same) | ✓ |
| `acde:fs` | `fs` | `fs` | ✓ |
| `acde:terminal` | `terminal`, approved by the user | `terminal` | ✓ |
| `acde:network` | `network`, approved by the user | `network` | ✓ |
| `acde:office` | `office` | `office` | ✓ |
| `acde:openPath` `acde:handlers` | `openFiles` | `openFiles` | ✓ |
| `acde:launch` | `launch` or `slots`, approved by the user | `launch` or `slots` | ✓ |
| `acde:windows` `acde:packages` `acde:session` `acde:desktops` `acde:inspect` `acde:desktop` `acde:setDefault` `acde:permissions` (shell modules) | | The module's name: `"windows": true` | ✓ |
| `acde:<service>` | The service's name in `services` | The same | ✓ |

A module the platform lacks is missing for everyone there (see [Platform support](https://docs.dopame.ai/reference/platforms.md)). An import that is not allowed fails with a `TypeError` whose message names the missing declaration, such as `acde:terminal needs "terminal" in the capabilities of Notes`. Desktop services cannot import `acde:` modules; a service that the desktop grants shell modules gets them from `ctx.import()`; see [Service API](https://docs.dopame.ai/reference/service.md).

Events are subscribed with `on(type, handler)`, which returns an unsubscribe function. `on()` throws a `TypeError` for an event type the module does not have, such as `acde:window has no nosuch event (activate, deactivate, …)`. Two modules take a callback instead: `acde:terminal` (`subscribe`) and `acde:network` (`watch`).

- Full screen is a state: `requestState('fullscreen')`. `requestMode('fullscreen')` throws a `TypeError`, and so does an unknown state. `requestState` has no result; follow the `state` event. See [Window state](https://docs.dopame.ai/guide/window.md#window-state).

- Coordinates are logical pixels of the page (the content area). Shortcut combos are written like `ctrl+alt+t`: keys are xkb keysym names, the key names X11 and Wayland use (`t`, `return`, `escape`, `f5`, `space`; case doesn't matter), and Shift is part of the combo.

## acde:capabilities

```ts
interface AcdeCapabilities {
  readonly level: number
  readonly platform: 'linux' | 'win32' | 'darwin'
  readonly mode: 'session' | 'desktop' | 'standalone'
  readonly window: { readonly backdrop: 'full' | 'approximated' | 'unsupported' }
  get(name: string): CapabilityStatus
  list(): CapabilityStatus[]

}

interface CapabilityStatus {
  name: string
  kind: 'system' | 'service'
  state: 'available' | 'not-asked' | 'asking' | 'not-declared' | 'unsupported' | 'service-not-running' | 'shell-only' | 'denied'

```

`level` is the contract level (1). `request(name)` asks the user for a capability that needs approval and resolves with its status after the answer; for anything else it resolves at once. A capability that needs approval is `available` only once the user allowed it: `not-asked` before the prompt, `asking` while it waits, `denied` after a denial or after the approval was taken back. A call that the approval stops fails with `status: 403`, the `capability`, and one of the codes `not_asked`, `asking`, `denied`. Names are capability names, `fs.<place>` for a shared place (`fs.downloads`), and service names. See [Capabilities](https://docs.dopame.ai/guide/capabilities.md#acdecapabilities).

## acde:fs

```ts
interface AcdeFs {
  roots(): Promise<FinderRoot[]>
  list(root: string, path?: string, hidden?: boolean): Promise<{ root: FinderRoot; path: string; entries: FinderEntry[]; truncated: boolean }>
  stat(root: string, path: string): Promise<FinderEntry & { path: string }>
  readText(root: string, path: string): Promise<{ text: string; modifiedMs: number; size: number }>
  readBytes(root: string, path: string): Promise<{ data: Uint8Array; modifiedMs: number; size: number }>
  writeFile(root: string, path: string, data: string | Uint8Array, options?: {
    create?: 'always' | 'new' | 'never'
    ifModifiedMs?: number
    mkdirs?: boolean
  }): Promise<FinderEntry>
  mkdir(root: string, path: string, options?: { recursive?: boolean }): Promise<FinderEntry>
  rename(root: string, from: string, to: string): Promise<FinderEntry>
  delete(root: string, path: string): Promise<{ status: 'deleted'; path: string }>
  copy(fromRoot: string, fromPath: string, toRoot: string, toDir: string): Promise<FinderEntry & { path: string }>
  preview(root: string, path: string): Promise<FinderPreview>
  download(root: string, path: string): Promise<{ name: string; contentType: string; data: Uint8Array }>
  revoke(root: string): Promise<void>
  locate(path: string): Promise<{ root: string; path: string }>
  openPath(root: string, path: string): Promise<{ root: string; path: string; file: string }>
}

interface FinderRoot {
  id: string
  label: string
  source: 'private' | 'place' | 'granted' | 'desktop' | 'downloads' | 'default' | 'task'
  place?: 'desktop' | 'documents' | 'downloads' | 'music' | 'pictures' | 'videos'
  path?: string
  mode: 'writable' | 'read_only' | 'unavailable'
  reason: string | null
  exists: boolean
}

interface FinderEntry {
  name: string
  kind: 'directory' | 'file' | 'symlink' | 'other'
  size: number
  modifiedMs: number
  target?: string
}

interface FinderPreview {
  path: string
  name: string
  size: number
  modifiedMs: number
  kind: 'text' | 'image' | 'binary' | 'too_large'
  content?: string
  truncated?: boolean
}
```

- `root` is the `id` of an item of `roots()`: `private`, a shared place's name, or `folder-…` for a picked folder; never a path. An app's roots have `source` `private`, `place` (with `place`), or `granted`, and no `path`.
- `path` is there only for system apps that name shared places, and for the desktop page. `locate` and `openPath` work only for them; in other apps they reject with `EACCES`.
- The desktop page's roots are folders by path (`source` `desktop`, `downloads`, `default`, `task`, or `granted`), and their `id` is the path.
- `list` includes hidden entries unless `hidden` is `false`.
- `copy` copies a file or a folder from one root into the folder `toDir` of another; a taken name gets a number (`todo 2.md`), and `path` is where the copy is in `toRoot`.
- `revoke` gives back a folder the user picked.
- Limits: `readText` / `readBytes` 64 MiB; `preview` text 256 KiB.
- `download` answers the type the system knows for the file's name as `contentType`: `text/markdown` for `note.md`, `image/png` for `shot.png`, and `application/octet-stream` for a name it knows no type for (`data.xyz`). The types come from the system, as described under [Files and links](https://docs.dopame.ai/guide/open.md#files-and-links).
- Errors have `code` and `status`; see [Files and folders](https://docs.dopame.ai/guide/files.md#errors).

## acde:open

```ts
interface AcdeOpen {
  (app: string, request?: null, options?: OpenWindowOptions): Promise<{ window: number }>
  <R extends AppRequest>(app: string, request: R, options?: OpenWindowOptions): Promise<{ window: number }>
  (app: string, request: SystemRequest): Promise<Opened>
  (request: SystemRequest): Promise<Opened>
}

type AppRequest<K extends string = string, Fields extends object = Record<never, never>> = { readonly kind: K } & { readonly [P in keyof Fields]: Fields[P] }

type SystemRequest =
  | { kind: 'open-file'; handle?: FileSystemFileHandle | FileSystemDirectoryHandle; url?: string; root?: string; path?: string; file?: string | null }
  | { kind: 'open-link'; url: string }

interface OpenWindowOptions { parent?: number; modal?: boolean }
interface Opened { kind: 'acde' | 'native'; id: string; window?: number }
```

- `open(app)` and `open(app, request)` need the `open` capability to allow `app`. A request to an app must have a `kind` that the target lists in its `requests` (400 `untyped_request`, 409 `not_accepted`).
- `open(request)` with a system request and no app needs `openFiles`: the system picks the app. With an app, the target must declare the file's type (`mimeTypes`) or the link's scheme (`schemes`).
- A receiving app gets a file as `{ kind: 'open-file', handle }`; a system app that names shared places also gets `url`. Send a file with `handle` (one this page got from a picker, a drop, or a request) or, where the caller knows paths, with `url`.
- A receiver types its own requests with `AppRequest<K, Fields>`: `type ShowImage = AppRequest<'show-image', { image: string }>`, then `self.on<ShowImage>('request', …)` narrows by `kind`. `SystemRequest` and `AppRequest` are also in `acde:window`'s `request` event (above).

See [Opening apps](https://docs.dopame.ai/guide/open.md).

| Event | Extra fields |
| --- | --- |
| `open` | `appId`, `title`, `web`, `icon` |

| `state` | `state`, `previous` |

```ts
  reason: 'launch' | 'request'
}

interface PermissionDecision {
  app: string
  label: string | null
  capability: string
  decision: 'granted' | 'denied'

}
```

`capability` is `launch`, `slots`, `terminal`, `network`, `camera`, `microphone`, or `fs.<place>`; in a decision it can also be `fs.folder-…`, a folder the user picked for the app (with `folder`). `reason` is `launch` for a prompt raised before an app starts and `request` for one raised by `capabilities.request()`. `revoke` resolves to `false` when there was no decision. # Service API

The default export of a desktop service module is a `ServiceFactory`. See [Services](https://docs.dopame.ai/guide/services.md) for usage.

```ts
type ServiceFactory = (context: ServiceContext) => ServiceInstance | Promise<ServiceInstance>

interface ServiceInstance {
  readonly api: Readonly<Record<string, object>>
  readonly sync?: readonly string[]
  close?(): unknown
}

interface ServiceContext {
  readonly name: string
  readonly package: string
  readonly state: string
  readonly native: Readonly<Record<string, unknown>> | null
  readonly env: Readonly<Record<string, string | undefined>>
  readonly inspect?: AcdeInspect
  log(line: string): void
  spawn(argv: readonly string[], options?: SpawnOptions): ServiceProcess
  import<K extends keyof ServiceModuleTypes>(specifier: `acde:${K}`): Promise<{ readonly default: ServiceModuleTypes[K] } & { readonly [N in K]: ServiceModuleTypes[K] }>
}

// ServiceModuleTypes: windows, packages, session, desktops, inspect, setDefault, and desktop with apps() only

interface SpawnOptions {
  readonly cwd?: string
  readonly env?: Readonly<Record<string, string>>
  onLine?(line: string): void
  onExit?(code: number | null, signal: number | null): void
}

interface ServiceProcess {
  readonly pid: number
  write(text: string): boolean
  end(): void
  kill(signal?: 'SIGTERM' | 'SIGKILL' | 'SIGINT' | 'SIGHUP'): boolean
}
```

- `api`: namespace → object. Each namespace becomes the module `acde:<namespace>`; functions on the object become callable methods, and strings / numbers / booleans become read-only fields.
- `sync`: a list of `"namespace.method"` entries. These methods are called once when a page starts, the results are cached in the page, and from then on they return synchronously in the page (good for configuration that doesn't change).
- `close()`: called when the desktop stops.
- An app lists the **service name** (the key in the desktop config's `services`) in its own `services`, and the runtime then gives it every namespace of that service. `acde check` and `acde build` let an import of a namespace that is not the service's own name pass with a `note:`, because they cannot know a service's namespaces (see [Services](https://docs.dopame.ai/guide/services.md#call-it)). A service name cannot be that of a system module or capability, and a namespace with such a name is left out.
- `import('acde:windows')`: resolves to the module (`{ windows, default }`) when the desktop grants it to this service: `"services": { "clock": { "module": "services/clock.ts", "modules": ["windows"] } }` in `acde.config.jsonc`, which `acde build` writes into the manifest as `"services": [{ "name": "clock", "modules": ["windows"] }]` (see [Manifest](https://docs.dopame.ai/reference/manifest.md#desktopmanifest)). Otherwise it rejects with `acde:windows is a shell module: list it in the modules of service "clock" in the desktop manifest`. A service cannot use a static `import` of an `acde:` module (the build rejects it). A service gets the modules a desktop page gets, with two exceptions: `acde:desktop` is `apps()` only, and `acde:permissions` is not given. Calls that the types declare as promises return promises in a service too. See [Services](https://docs.dopame.ai/guide/services.md#shell-modules-in-a-service).

```ts
  text: string

```

- `launch` starts an `acde dev` session on the project's own runtime (Bun or Node.js) and waits until the windows of all pages have appeared, or an approval prompt waits (`startTimeout`, 120 seconds by default). When the session does not start, it ends that `acde dev` and throws a `LaunchError` (an `Error`, exported by `acde/driver`). Its message says how far the start got and ends with the last 40 lines of the output of `acde dev`; `logs` holds the whole output (`error.logs.tail(5000).text`), and `phase` is:
  - `'exited'`: `acde dev exited (1) before it was ready:`; `code` is the exit code (`null` in the other phases).
  - `'session'`: `acde dev (pid 4242) did not register a session within 120 s in <dir>`, then the line `no session yet: its build did not finish, or acdert did not start listening; last output:`.
  - `'window'`: `acde dev did not start within 120 s:`, then the line `acdert runs and answers, but no window appeared (pages: 0, windows: 0) and no approval prompt waits; last output:`.
  - `'failed'`: anything else that went wrong while it waited (the message is that error's, which is also the `cause`).
- `close()` ends the session that `launch` started: it sends SIGTERM, then SIGKILL after 10 seconds. On a session from `attach` it only disconnects.
- `act` answers `ok: false` when the action was not done. In a session that runs a single app, closing the app's only window ends the session, by design: the `close` that did it resolves with `ok: true`, `ended: true` and the text `closed w1; acdert exited with it, so acde dev <pid> ended`; `closed` becomes true, and every later request rejects with `acde dev <pid> is no longer connected`. Any other request during which the runtime goes away rejects with `acdert closed the connection` (also a `close` in a desktop session, and a `run` whose steps close the window).
- `choose*` answers, in advance, the **next** picker of that kind the page opens; `null` means the user cancelled; relative paths resolve against the current directory.
- Call `waitFor*` before the action that triggers it.
- `addInitScript` registers code that runs before a page's own scripts on every load (`once`: on the next load only); `web` is a page name or an app id, and without it every page runs the code. It returns an id for `removeInitScript`, which removes every script when no id is given.
- `answerDialog` answers the page's next `alert` / `confirm` / `prompt` in advance: `accept: false` cancels, `text` is what a `prompt` answers. Without an answer `confirm` gives false and `prompt` null. `Dialog` is `{ type, message, defaultValue, answered, accept, text }`.
- `input` sends raw events at page coordinates: `{ type: 'move' | 'down' | 'up' | 'wheel', x, y, button?, dx?, dy? }`, `{ type: 'keydown' | 'keyup', key }` and `{ type: 'text', text }`. `app.mouse` and `app.keyboard` are built on it.
- Approval prompts (`PermissionPrompt` is `{ id, app, label, capability, reason: 'launch' | 'request' }`, `PermissionDecision` is `{ app, label, capability, decision: 'granted' | 'denied' }`): `allow` and `deny` wait for a prompt that matches (any prompt when nothing is given), answer it and return it; `waitForPrompt` only waits; `answer` answers a prompt you already have. Nothing answers a prompt by itself: an app whose required capability waits has no window until the test answers. `revoke` takes a decision back and returns whether there was one. See [Approvals in tests](https://docs.dopame.ai/guide/testing.md#approvals).
- `drop` drops files from the system onto a page (default: the middle of the desktop page; `web` picks a page, `x` and `y` a point in it). The page gets a standard `drop` event a moment after the call returns, so wait for what the page does with it.

`AppWindow` looks itself up in the window table again on every use, so it keeps working if the window is closed and reopened.

`info()` is the window's row in that table: `ref`, `id`, `app`, `title`, `state` (`normal`, `minimized`, `filled`, `fullscreen`), `focus`, `hidden` and more. While a window is minimized, `state` is `minimized`, `hidden` is `true`, and locators find no element in it: `toBeHidden()` passes, and an action waits until its timeout (`no element matches`). `restore()` brings the window and its elements back.

`reload()` waits until the new page has loaded; `resize()` sets the size of the page without the title bar and waits until `innerWidth` and `innerHeight` have it (a window that fills the screen resizes the host window, which Windows cannot do yet); `seedLocalStorage()` writes the entries before the page's scripts run, by reloading the page once.

Coordinates are CSS pixels of the page, as `getBoundingClientRect()` gives them. `ControlOrMeta` is `Control` on every system. ### Semantic tree limitations

`getByRole`, `getByText` and `getByLabel` search the runtime's semantic tree, not the DOM:

- Elements with `opacity: 0` are not in it, so these locators do not find them.
- `getByText` compares accessible names.

CSS locators (`locator`, `getByTestId`, `getByPlaceholder`, `getByTitle`, `getByAltText`) search the DOM and also match elements that are not rendered; `toBeVisible`, `toBeHidden`, `isVisible()` and `waitFor({ state })` tell the two apart, and actions wait until the element is rendered.

# Web compatibility

acdert has its own renderer (it is not Chromium), and page JS runs in its embedded V8. The rule is that **standard APIs are fully browser-compatible**: behavior, signatures, events, and errors all follow the spec. Anything that can't be done that way is a gap; it is not filled with a look-alike proprietary version. Below are the things worth knowing.

## Origin

Every app page has the origin `http://acde.local`. Each app's storage is a separate partition, invisible to other apps.

## Storage

| API | Notes |
| --- | --- |
| `localStorage` | Shared by all windows of the same app; 5 MiB quota; other windows get a `storage` event on changes |
| `sessionStorage` | Per window, in memory only; **not** kept across `location.reload()` (unlike browsers) |
| IndexedDB | Fully implemented, stored in SQLite; promise-wrapper libraries (idb and others) behave as in browsers |
| Cache API | `caches` is supported |
| cookie | Stored and sent as usual for same-origin requests (your own backend); cross-origin requests neither send nor store cookies |
| `navigator.storage` | `estimate()`; `persist()` is always `true`; `getDirectory()` is the origin private file system (OPFS) |

Data lives in `$XDG_DATA_HOME/acde/storage/app-<id>/`.

## Network

- `fetch`, `XMLHttpRequest`, `WebSocket`, and `EventSource` are all supported.
- Same-origin paths and `localhost` go to the app's own backend; see [Backend](https://docs.dopame.ai/guide/backend.md).
- Requests to other hosts use the system's DNS and network, with normal certificate validation, and go through a proxy the way the system says: with `http_proxy`, `https_proxy` or `all_proxy` set in the session, only those variables (and `no_proxy`) count; otherwise the system's proxy settings (Windows: the user's Internet settings, including a configuration script and automatic detection; macOS: the network settings; Linux has no other source). `localhost`, loopback addresses and the app's own backend are always reached directly. Proxy authentication and `https://` proxies are not supported. Responses are not decompressed automatically (no `Accept-Encoding` is sent).
- Cross-origin requests follow browser rules: `Origin` header, CORS preflight, response header filtering, opaque responses for `no-cors`.
- Forbidden request headers (`Host`, `Cookie`, `Origin`, `Referer`, `Sec-*`, ...) are not sent even if you set them.
- Synchronous XHR can only read the app's own files.

## External resources

Images (`<img>` and images in CSS), stylesheets (`<link rel="stylesheet">`) and fonts load from other hosts as they do in a browser: images and stylesheets without CORS, fonts only with an `Access-Control-Allow-Origin` that allows the page, a stylesheet only from a 2xx `text/css` response. They show up in `acde network` with the kinds `image`, `stylesheet` and `font`, and a failed one is a console error `Failed to load resource: <url>: <reason>`. A `<link rel="stylesheet">` fires `load` once its sheet is fetched and applied and `error` when it cannot be had (also when a sheet it `@import`s cannot); `link.sheet` and `document.styleSheets` have the sheet from then on. The rules of a sheet from another host (`sheet.cssRules`) throw `SecurityError` unless the link has `crossorigin` and the host allows the page with `Access-Control-Allow-Origin`. **ES modules can't be `import`ed from other hosts** (`module … is not a local file`): bundle the code you depend on into the app. (Classic `<script src>` can load from other hosts.) An app that should work without a network bundles its images, styles and fonts too.

## Scripts

Classic `<script>`, `type="module"`, and `type="importmap"` are supported.

## File pickers

`showOpenFilePicker`, `showSaveFilePicker`, `showDirectoryPicker`, and `<input type="file">` open the system dialog; see [Files and folders](https://docs.dopame.ai/guide/files.md).

Files and folders dropped into a window arrive the standard way: `dataTransfer.files`, and a read-only handle from `dataTransfer.items[i].getAsFileSystemHandle()`. Folders and files over 64 MiB are not in `files`; use the handle. See [Dropped files](https://docs.dopame.ai/guide/files.md#dropped-files).

## Media

`Audio` / `AudioContext` are supported. WebGPU is currently available only on Linux.

`<video>` plays what the system's own decoders can open, so formats differ by platform: on macOS, MP4 / QuickTime plays and WebM does not. Ask `canPlayType()` before choosing a source.

`navigator.mediaDevices.getUserMedia()` needs the `camera` / `microphone` capability in the config and the user's approval (see [Capabilities](https://docs.dopame.ai/guide/capabilities.md#approval)). Not available on Windows.

- A required capability is approved before the app starts. An [optional](https://docs.dopame.ai/guide/capabilities.md#optional-capabilities) one that was not asked for yet is asked for by `getUserMedia()` itself, with the prompt `request('camera')` raises; a call that wants both asks for the microphone first, then the camera. The call resolves once the user allows and rejects with `NotAllowedError` (`Permission denied`) when the user denies; later calls do not ask again.
- `navigator.permissions.query({ name: 'camera' })` (or `'microphone'`) answers `prompt` until the user has answered and `denied` after a denial or after the approval was taken back; its `change` event fires on the answer. Once the user has allowed it, the answer is the host system's own permission for the device (`granted` when the system allows it too).
- In an app that does not declare the capability, the query answers `denied` and `getUserMedia()` rejects with `NotAllowedError`, without a prompt.
- Constraints are judged first: a request that no device can meet rejects with `OverconstrainedError` and asks nobody.
- `enumerateDevices()` lists one entry without a label for a kind that is not allowed yet.
- To try a page without a real camera or microphone, start the session with `ACDE_CAPTURE=fake`: the devices are then `Fake camera` and `Fake microphone`.

## Not yet supported

`<datalist>`, `appearance: base-select` on `<select>`, Web Workers, `crypto.subtle`, WebGL (`getContext('webgl')` and `getContext('webgl2')` return `null`; use 2D canvas, or WebGPU on Linux), OffscreenCanvas / `createImageBitmap`, the Fullscreen API (`requestFullscreen()` rejects with `NotSupportedError`; an app window goes full screen with `requestState('fullscreen')` from [`acde:window`](https://docs.dopame.ai/guide/window.md#window-state)) and pointer lock, `:target`, Storage Buckets, and Service Workers.

## Differences from browsers

- `alert()` is drawn inside the window; `confirm()` returns `false` and `prompt()` returns `null`.
- `navigator.userAgent` and `navigator.platform` say Linux on every system (`Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) acdert/<version>` and `Linux x86_64`), and editing shortcuts use Ctrl everywhere, so an app behaves the same on every host. To know the real system, read `platform` from [`acde:capabilities`](https://docs.dopame.ai/guide/capabilities.md#acdecapabilities).
- There are no developer tools: use the [debugging tools](https://docs.dopame.ai/guide/tools.md) and [MCP](https://docs.dopame.ai/guide/mcp.md).
- Pages have no security sandbox (there is no syscall-level isolation yet): don't run code you don't trust.

# Platform support

The host window used for development (`acde dev`) runs on macOS, Windows, and Linux; Dopame OS itself is Linux. The runtime is built for macOS on Apple silicon and Intel, Linux on x86_64, and Windows on x64; see [Install](https://docs.dopame.ai/start/install.md#supported-platforms).

| | macOS | Windows | Linux (development) | Dopame OS |
| --- | --- | --- | --- | --- |
| Page rendering (requires a GPU) | Metal | DX12 | Vulkan (a hardware driver) | Vulkan |
| `acde:fs`, file pickers | ✓ | ✓ | ✓ | ✓ |
| Sound, clipboard | ✓ | ✓ | ✓ | ✓ |
| System notifications | ✓ | Only in a desktop, which shows them | ✓ | Shown by the desktop |
| App backends | ✓ | ✓ (see [Backend](https://docs.dopame.ai/guide/backend.md#on-windows)) | ✓ | ✓ |
| `acde:terminal` (`terminal`) | ✓ | ✓ | ✓ | ✓ |
| Camera and microphone (`camera`, `microphone`) | ✓ | | ✓ | ✓ |
| `acde:network`, `acde:office` (`network`, `office`) | | | ✓ | ✓ |
| Native programs embedded in a window (`slots`) | | | | ✓ |
| WebGPU, voice input | | | ✓ | ✓ |
| Native programs (`.desktop`) | | | ✓ | ✓ |
| Headless (`--headless`, `acde test`) | ✓ | ✓ | ✓ (requires a GPU) | |

- Capabilities a platform lacks are not faked. An app that **requires** one does not start there (`Notes needs "network" (unsupported on this platform)`) and is left out of the app list; one that lists it in `optional` starts, `load()` gives `null` for the module, and `acde:capabilities` reports `state: 'unsupported'`. See [Capabilities](https://docs.dopame.ai/guide/capabilities.md#optional-capabilities).
- `acde check --platform windows` (or `macos`, `linux`) tells you before you run there: `error: macos (standalone): app "notes" requires network, which this mode lacks`, or a `note:` when the capability is optional. The data is `PLATFORM_SUPPORT` in `@dopame/acde-api`, per platform and way of running: `session` (Dopame OS), `desktop` (a desktop in the host window), `standalone` (a single app in the host window). A page reads its own from `acde:capabilities` (`platform`, `mode`).
- The runtime draws pages only on the GPU, so Linux CI without a GPU cannot run headless. macOS CI runners can.
- On Linux the runtime needs the **hardware Vulkan driver** of the machine's GPU; a software renderer (lavapipe / llvmpipe) is not accepted. Without one, `acde dev` fails at startup with a log line that says so and names the GPU the system has: `web layer unavailable: the system has a GPU (card0, kernel driver i915) but no usable Vulkan driver was found: install the GPU's Vulkan driver (for example vulkan-intel, vulkan-radeon, nvidia-utils) or point VK_DRIVER_FILES at its ICD (…)`. The fix is to install the driver, then check that `vulkaninfo --summary` lists the GPU: for Mesa, `vulkan-intel` or `vulkan-radeon` on Arch, `mesa-vulkan-drivers` on Debian, Ubuntu and Fedora; for NVIDIA, the vendor's driver.
